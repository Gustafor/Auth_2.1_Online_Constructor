### Описание шагов

#### Шаг 1. 1.1 · Пользователь нажимает «Войти»

**Что происходит**

Клик по кнопке «Войти» — единственное действие этого шага: браузер шлёт GET /login на ваше приложение. На этом шаге не происходит ни обмена токенами, ни обращения к AS: приложение проверяет, есть ли у пользователя уже живая сессия (HttpOnly-cookie + токен в хранилище на бэкенде), и только потом решает, нужен ли вообще редирект на AS. Зачем это важно: Auth 2.1 — про поток, и запускать его повторно при уже валидной сессии лишний раз тратит код, cookie AS и сессии (риск «расщепления» сессий). Кнопка «Войти» должна быть идемпотентна: двойной клик не создаёт два потока, а второй запрос упирается в уже существующую сессию.

**Подписи стрелок этого шага**

  • Браузер → Приложение (РП): 1.1 GET /login (клик «Войти»)

**Что делаете вы (реализация)**

- Перед редиректом проверьте валидность текущей сессии (нет сессии → запуск потока; есть и живая → 200 сразу)
- Делайте кнопку идемпотентной: двойной клик не создаёт второй поток (первый запрос уже открыл сессию)

**HTTP-трафик / код**

```
GET /login
→ 401 (сессии нет)
WWW-Authenticate: Bearer error="invalid_token",
  error_uri="https://as.example/oauth-error"
```

#### Шаг 2. 1.2 · RP генерирует «бумажки» и прячет в сессии

**Что происходит**

Приложение генерирует три случайных значения и кладёт их в серверную сессию до редиректа: state (128 бит, защита от CSRF), nonce (128 бит, привязка ID-токена к этому конкретному запросу, защита от replay) и code_verifier (43–128 символов из [A-Za-z0-9-._~], RFC 7636 §4.1). Из code_verifier считается code_challenge = BASE64URL(SHA256(code_verifier)) — метод строго S256, плановый plain запрещён для всех веб-клиентов. Критично: в сессию уходит именно verifier (секрет), а в будущий URL — только challenge (публичная «половинка»). Генерация — только CSPRNG: crypto.randomBytes (Node) или crypto.getRandomValues (браузер). Math.random() запрещён — предсказуемый state/nonce = CSRF и replay на уровне протокола.

**Подписи стрелок этого шага**

  • **Приложение (РП)** (собственное действие): 1.2 state · nonce · code_verifier → сессия

**Что делаете вы (реализация)**

- Генерация: crypto.randomBytes(32) → state, nonce; verifier из базы RFC 7636 (32 байта → base64url)
- state, nonce, verifier — в серверную сессию (HttpOnly); в URL и в frontend-хранилища — только challenge

**HTTP-трафик / код**

```
// Node: генерация до редиректа
const state  = crypto.randomBytes(16).toString("hex");
const nonce  = crypto.randomBytes(16).toString("hex");
const ver    = base64url(crypto.randomBytes(32)); // 43 симв.
const chal   = base64url(sha256(ver)); // S256
req.session.auth = { state, nonce, ver };
```

#### Шаг 3. 1.3 · 302 редирект на /authorize

**Что происходит**

Приложение отвечает браузеру 302 Found, и Location — полный URL authorization_endpoint (из discovery документа AS, никогда не хардкод). В query — только ПУБЛИЧНЫЕ параметры: client_id, redirect_uri (побайтово как в регистрации AS, RFC 9700 §2.1), response_type=code, scope=openid+profile+email, state (из сессии), nonce (из сессии), code_challenge + code_challenge_method=S256. code_verifier в этом URL отсутствовать ДОЛЖЕН — это секрет шага 1.2. 302, а не 200-с-JS-редиректом: JS-редирект оставляет текущий URL в истории и логах, а 302 — стандартный механизм передачи управления браузеру.

**Подписи стрелок этого шага**

  • Приложение (РП) → Браузер: 1.3 302 /authorize · code_challenge (публичная)

**Что делаете вы (реализация)**

- Соберите URL из discovery-метаданных, redirect_uri — побайтово как зарегистрирован (scheme, host, порт, путь, без хвостового /)
- Проверьте свой Location перед отправкой: в нём нет code_verifier

**HTTP-трафик / код**

```
302 Found
Location: https://as.example/authorize
  ?client_id=web-app-01
  &redirect_uri=https://app.example/callback
  &response_type=code&scope=openid+profile+email
  &state=9f2ab7…&nonce=41c3d0…
  &code_challenge=E9Melhoa2Owv…
  &code_challenge_method=S256
```

#### Шаг 4. 2.1 · Браузер ходит на /authorize

**Что происходит**

Браузер выполняет редирект и отправляет GET /authorize на AS — запрос делает браузер, не бэкенд приложения. AS получает в query всё, что приложение отправило на шаге 1.3: client_id, redirect_uri, response_type, scope, state, nonce, code_challenge, method. AS на этом шаге Ничего не шлёт приложению: он лишь записывает challenge в привязку к сессии (это потребуется на шаге 4.2). state и nonce AS намеренно не использует — он их только пересылает обратно (шаг 3.1), чтобы приложение само сверило. Если redirect_uri не совпадает с зарегистрированным побайтово — AS ответит 400 invalid_request, а не 302 с ошибкой (так предотвращается open redirect).

**Подписи стрелок этого шага**

  • Браузер → Сервер авторизации (АС): 2.1 GET /authorize (scope=openid · nonce)

**Что делаете вы (реализация)**

- authorization_endpoint берите из discovery, не хардкод
- redirect_uri — побайтово как в регистрации: scheme, host, порт, путь; хвостовой «/» и query-параметры ломают совпадение

**HTTP-трафик / код**

```
GET /authorize?client_id=web-app-01
  &redirect_uri=https://app.example/callback
  &response_type=code&scope=openid+profile+email
  &state=9f2ab7…&nonce=41c3d0…
  &code_challenge=E9Melhoa2Owv…
  &code_challenge_method=S256  HTTP/1.1
Host: as.example
```

#### Шаг 5. 2.2 · AS: проверка сессии, вход, MFA

**Что происходит**

AS проверяет собственную сессию по СВОЕЙ cookie (не cookie приложения — у AS и RP разные домены, cookie друг другу не видны). Нет сессии или prompt=login → AS показывает форму входа. Пользователь вводит логин/пароль (+MFA, если включена). После успешной аутентификации AS ставит СВОЮ cookie: HttpOnly, Secure, SameSite=Lax (не None) — и записывает auth_time. auth_time позже попадёт в ID-токен и позволит приложению доказать, что пользователь аутентифицирован именно сейчас, а не 3 часа назад. Пароль в этом шаге видит только AS; приложение никогда не получает credentials — это фундаментальное разделение OAuth: RP доверяет AS как «человек этот — тот, кто он говорит».

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): 2.2 сессия? нет → вход · MFA

**Что делаете вы (реализация)**

- Cookie AS: HttpOnly; Secure; SameSite=Lax (не None, если cross-site не требуется)
- Записывайте auth_time при каждой аутентификации — он нужен для step-up-логики (вкладка Step-Up)

**HTTP-трафик / код**

```
POST /login (браузер → AS)
→ 302 + Set-Cookie: as_session=…; HttpOnly; Secure; SameSite=Lax
AS фиксирует auth_time=2026-11-05T12:00:00Z
```

#### Шаг 6. 2.3 · Экран согласия (consent)

**Что происходит**

AS показывает, ЧТО именно приложение запрашивает у пользователя: список scope в человеческом виде («profile — имя и аватар; email — адрес; openid — обязательный маркер OIDC»). Пользователь принимает или отказывается. При согласии — AS запоминает решение (consent record: client_id + user + scope + время) и идёт к генерации кода. При отказе — 302 на redirect_uri с error=access_denied&state={state}: браузер всё равно уходит на callback приложения, и приложение обязан обработать error-ответ так же, как code-ответ (шаг 3.2). Consent не обязан повторяться при каждом входе (AS сам решает по политике), но для чувствительных scope (address, phone) повторный запрос — лучшая практика. «Разрешить по умолчанию» — не вариант: пользователь должен видеть, ЧТО он разрешает.

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): 2.3 consent: profile + email → «Разрешить»

**Что делаете вы (реализация)**

- Запоминайте consent в AS, но для чувствительных scope (address, phone) запрашивайте повторно или раз в 90 дней
- Обработайте error=access_denied на callback так же, как code: сверка state обязательна

**HTTP-трафик / код**

```
GET /authorize → (AS показывает экран)
profile — имя, аватар
email — адрес
[ Разрешить ]  [ Отклонить ]
— отказ → 302 https://app.example/callback
  ?error=access_denied&state=9f2ab7…
```

#### Шаг 7. 2.4 · AS генерирует одноразовый code

**Что происходит**

После согласия AS генерирует authorization code — случайную строку (≥128 бит энтропии) и привязывает её к конкретному набору: client_id + redirect_uri (побайтово) + code_challenge + nonce + срок жизни 60–300 секунд. Code — это НЕ токен: он не несёт данных о пользователе и не даёт доступа ни к чему. Его единственная функция — быть одноразовым «талоном», который приложение обменяет на токены по защищённому каналу (шаг 4.1). Привязка к challenge означает: этот код нельзя обменять без code_verifier, из которого challenge вычислен. Привязка к nonce означает: ID-токен, который будет выдан за этот код, будет содержать ровно тот nonce, что в запросе /authorize (защита от replay ID-токена). TTL 60–300 с: если пользователь закрыл браузер на середине, код сгорит сам.

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): 2.4 code → привязка к challenge + nonce

**Что делаете вы (реализация)**

- Храните code в отдельной таблице/кэше AS со ссылкой на сессию: {code, client_id, redirect_uri, challenge, nonce, exp}
- TTL 60–300 с; после обмена — строка удаляется (single-use на уровне хранилища)

**HTTP-трафик / код**

```
AS: codes.insert({
  code: "SplxlOBeZQQYbYS6WxSbIA",
  client_id: "web-app-01",
  redirect_uri: "https://app.example/callback",
  challenge: "E9Melhoa2Owv…",
  nonce: "41c3d0…",
  exp: now + 300s })
```

#### Шаг 8. 3.1 · AS редиректит с кодом

**Что происходит**

AS отвечает браузеру 302 на redirect_uri приложения с ДВУМЯ параметрами: code (одноразовый талон) и state (то самое значение, что пришло в /authorize, без изменений). Это единственный URL-переход, в котором летит code — и он летит в адресной строке браузера, то есть потенциально попадает в историю, Referer, логи прокси. Поэтому code должен быть короткоживущим (шаг 2.4) и одноразовым (шаг 4.2). Токены в этом URL НЕТ: access_token и id_token здесь не передаются — только code. Если вместо кода AS вернул error (например, access_denied), в URL будет error=…&error_description=…&state=… — и приложение обязано это обработать (шаг 3.2). redirect_uri в 302 должен побайтово совпасть с тем, что был в /authorize, иначе AS не шлёт code вовсе (защита от open redirect).

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Браузер: 3.1 302 callback?code=…&state=…

**Что делаете вы (реализация)**

- В URL — только code + state; токены никогда не летят через браузер
- Redirect URI в 302 проверяется AS побайтово — при несовпадении code не выдаётся

**HTTP-трафик / код**

```
302 Found
Location: https://app.example/callback
  ?code=SplxlOBeZQQYbYS6WxSbIA
  &state=9f2ab7…
```

#### Шаг 9. 3.2 · Браузер достаёт code у RP

**Что происходит**

Браузер выполняет 302 и приходит на callback приложения с GET /callback?code=…&state=…. ВНИМАНИЕ: с этого момента code находится в зоне ответственности приложения — а не AS. Всё, что приложение с ним сделает (или не сделает), — проблема приложения. Первый код в query-string означает, что code уже побывал в адресной строке, в истории браузера, в потенциальных Referer-заголовках. Задача приложения на этом шаге — немедленно забрать code из query, убрать его из URL (history.replaceState, чтобы не остался в истории), и НЕ записывать его в логи. Код живёт 60–300 секунд (шаг 2.4), поэтому обмен должен начаться сразу, а не «когда-нибудь потом». Если в query вместо code пришёл error — это тоже callback-ответ: приложение обрабатывает error и state, показывает пользователю причину (access_denied, server_error) и не пытается обменять code.

**Подписи стрелок этого шага**

  • Браузер → Приложение (РП): 3.2 GET /callback?code&state

**Что делаете вы (реализация)**

- Забрать code из query, history.replaceState убрать его из адресной строки
- НЕ писать code в логи/метрики/trace — он в URL, а URL логируется везде

**HTTP-трафик / код**

```
GET /callback?code=SplxlOBeZQQYbYS6WxSbIA&state=9f2ab7…
// приложение:
const { code, state } = req.query;
// code НЕ логируется; дальше — шаг 3.3 (state), 4.1 (обмен)
```

#### Шаг 10. 3.3 · ПРОВЕРКА STATE (важный шаг)

**Что происходит**

Прежде чем что-либо делать с code, приложение сверяет state из URL с тем, что сгенерировало на шаге 1.2 и хранило в серверной сессии. Сравнение — по времени (timingSafeEqual), а не ===: === уязвим к timing-атакам на уровне байтов. Совпало — code «наш», поток честный, идём на шаг 4.1. НЕ совпало — это CSRF: кто-то заставил браузер пользователя пройти чужой /authorize (например, атакующий открыл ссылку со СВОИМ state и СВОИМ code, и victim-браузер принёс чужой code на callback жертвы). Приложение: 400, уничтожить сессию, НЕ обменивать code, залогировать инцидент. Этот шаг — единственная линия защиты от CSRF в OAuth: без сверки state атакующий может привязать ЧУЖУЮ учётку к СВОЕЙ сессии (login CSRF). state ≠ «красивый UUID для красоты» — это криптографическая привязка «этот code — ответ на МОЙ запрос».

**Подписи стрелок этого шага**

  • **Приложение (РП)** (собственное действие): 3.3 сверка state ↔ сессия · нет → 400 (CSRF)

**Что делаете вы (реализация)**

- Сравнение: crypto.timingSafeEqual(Buffer.from(a), Buffer.from(b)) — никогда ===
- Mismatch → 400 + destroy session + лог инцидента; code НЕ обменивается

**HTTP-трафик / код**

```
const ok = crypto.timingSafeEqual(
  Buffer.from(req.query.state),
  Buffer.from(req.session.auth.state));
if (!ok) { req.session.destroy(); return 400; }
// ок → код «наш», идём на /token
```

#### Шаг 11. 4.1 · RP шлёт POST /token с верификером

**Что происходит**

Приложение (бэкенд, НЕ браузер) делает server-to-server POST на token_endpoint по TLS. В body (application/x-www-form-urlencoded): grant_type=authorization_code, code (из callback), redirect_uri (то же самое, что в /authorize — AS сверит), code_verifier (из сессии, НЕ из query — verifier не должен никуда «уходить» после сессии). Аутентификация клиента: по Auth 2.1 для конфиденциальных клиентов — private_key_jwt или mTLS (client_secret в POST body не рекомендуется; см. вкладку «Авторизация клиента»). Таймаут — 10 секунд: если AS не ответил, запрос повторяется, но code уже может быть использован (single-use), поэтому повтор — только после явной 4xx/5xx, а не по таймауту слепым. Этот канал (бэкенд → AS) — отдельный от канала браузера: здесь нет cookie AS, нет пользователя, только клиент и его аутентификация.

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): 4.1 POST /token (code + code_verifier)

**Что делаете вы (реализация)**

- POST body: grant_type, code, redirect_uri, code_verifier; Content-Type: application/x-www-form-urlencoded
- client_auth: private_key_jwt (заголовок Authorization) или mTLS; таймаут 10 с; повтор — только по явной 4xx, не по таймауту

**HTTP-трафик / код**

```
POST /token  HTTP/1.1
Host: as.example
Content-Type: application/x-www-form-urlencoded
Authorization: Bearer <JWT-assertion>

grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&redirect_uri=https://app.example/callback
&code_verifier=dbBgzZ1…zP5bFg
```

#### Шаг 12. 4.2 · AS валидирует: single-use + PKCE

**Что происходит**

AS выполняет ТРИ проверки перед выдачей токенов, и каждая — атомарна: (1) code существует, не истёк (TTL 60–300 с) и не использован — AS АТОМАРНО удаляет строку code из хранилища (DELETE WHERE code=… AND used=0; affected rows = 1 — только тогда продолжаем; это и есть single-use на уровне БД). (2) client, который пришёл (по assertion/mTLS) — тот самый client_id, к которому code был привязан на шаге 2.4. (3) SHA256(code_verifier из запроса) == code_challenge из привязки — это PKCE-проверка (RFC 7636 §4.6): без секретного verifier challenge не перебрать (SHA256 — односторонняя, 256 бит). Любая из трёх сбоев → 400 с конкретным error (invalid_grant, invalid_client, или 400 с описанием) и токены НЕ выдаются. Повторное использование code (та же строка, уже использованная) — красный флаг: AS обязан отозвать ВСЕ токены, уже выданные по этому code (reuse detection, как в refresh-ротации).

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): 4.2 code single-use · SHA256(verifier)==challenge

**Что делаете вы (реализация)**

- DELETE … WHERE code=… AND used=0 — атомарно; affected rows=1 → продолжаем
- SHA256(verifier) == challenge (RFC 7636 §4.6); reuse code → revoke всех токенов по этому code

**HTTP-трафик / код**

```
AS: 1) code: exists? exp? → DELETE (atomic)
    2) client_id == привязка?
    3) sha256(verifier) == challenge?
— всё ок → 200 + токены
— сбой → 400 { "error": "invalid_grant" }
```

#### Шаг 13. 4.3 · RP получает токены и сохраняет

**Что происходит**

AS отвечает 200 с JSON: access_token, id_token, refresh_token, token_type=Bearer, expires_in (обычно 300–3600 с), scope (то, что реально выдано — может быть уже запрошенного). Приложение обязано проверить: (1) статус 200 (не 204/302 — если AS вернул не 200 с телом, это ошибка интеграции), (2) ВСЕ три токена на месте (если refresh_token не дали, а заявлен — разбирать: scope без offline_access?), (3) expires_in записать — это триггер для refresh (шаг 7.1). Хранение: серверная сессия (HttpOnly) или шифрованное хранилище; localStorage и не-HttpOnly cookie — запрещены (XSS заберёт токены). access_token — для API (шаг 6.1), id_token — для проверки личности (шаг 5.1), refresh_token — для обновления (шаг 7.1). Токены НЕ отправляются в браузер: браузеру нужен только «вы вошли» (cookie сессии приложения).

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Приложение (РП): 4.3 200: access · id · refresh (форма → сессия)

**Что делаете вы (реализация)**

- Проверьте 200 + наличие access/id/refresh; запишите expires_in как триггер refresh
- Храните в HttpOnly-сессии/шифрованном хранилище; localStorage и не-HttpOnly — запрещены

**HTTP-трафик / код**

```
200 OK
{
 "access_token": "eyJhbG…J9",
 "id_token": "eyJhbG…QzI5",
 "refresh_token": "M42dG6…",
 "expires_in": 3600,
 "token_type": "Bearer",
 "scope": "openid profile email" }
```

#### Шаг 14. 5.1 · Проверка подписи и клеймов ID-токена

**Что происходит**

ID-токен — JWT, который AS подписал СВОИМ приватным ключом. Приложение проверяет его ЛОКАЛЬНО (без обращения к AS): (1) подпись — публичным ключом из JWKS AS (см. вкладку «Проверка токена»), kid из заголовка JWT выбирает ключ; (2) alg — белый список RS256/ES256, alg=none ОТКЛОНЯТЬ (классическая уязвимость); (3) iss == issuer из discovery (не «похожий» домен, а побайтово); (4) aud содержит client_id приложения; (5) exp > now (с допуском на clock skew 30 с); (6) iat <= now + skew; (7) nonce == nonce из шага 1.2 (защита от replay ID-токена: подделанный/перехваченный ID-токен из ЧУЖОГО потока не пройдёт по nonce). После успешной проверки приложение извlecает из payload: sub (идентификатор пользователя в AS), email, name, picture, auth_time, amr, acr, sid. Это и есть «профиль пользователя» — всё, что приложение знает о человеке, придёт из ID-токена. Подпись гарантирует: это именно AS подписал, и payload не менялся.

**Подписи стрелок этого шага**

  • **Приложение (РП)** (собственное действие): 5.1 jwtVerify: подпись JWKS · iss · aud · exp · nonce

**Что делаете вы (реализация)**

- jwtVerify: подпись (JWKS, по kid) + iss (побайтово) + aud (содержит client_id) + exp/iat (skew 30 с) + nonce
- alg — белый список RS256/ES256; none → отклонить

**HTTP-трафик / код**

```
// jose (Node)
const { payload, header } = await jwtVerify(
  idToken, jwksClient(discovery.jwks_uri), {
   issuer: discovery.issuer,
   audience: "web-app-01",
   algorithms: ["RS256","ES256"],
   nonce: req.session.auth.nonce });
// payload.sub, .email, .name, .auth_time, .sid
```

#### Шаг 15. 6.1 · Запрос данных с access-токеном

**Что происходит**

Приложение (или фронтенд от имени приложения, если API публичный) делает GET к API-ресурсу с заголовком Authorization: Bearer {access_token}. По RFC 6750 токен передаётся ТОЛЬКО в этом заголовке: в query-параметре (?token=…) — нельзя (попадёт в логи, историю, Referer), в форме — нельзя, в кукке — нельзя. API на этом шаге не знает, КТО пользователь: для API access_token — не «человек», а «набор разрешений (scope), привязанный к client и, если есть, к user». Приложение уже проверило id_token (шаг 5.1) и знает sub; API проверит свой участок: подпись (если API != AS и токен JWT — по JWKS), aud (содержит ли API в aud), exp, scope (хватает ли на операцию). Если токен в query — API обязан отклонить (RFC 6750 §2.3: resource server MAY reject).

**Подписи стрелок этого шага**

  • Приложение (РП) → API (ресурс): 6.1 GET /orders · Authorization: Bearer ***

**Что делаете вы (реализация)**

- Только Authorization: Bearer <token>; query/форма/cookie — недопустимы (RFC 6750 §2.3)
- Если API ≠ AS и AT — JWT: проверяйте подпись по JWKS + aud + exp + scope

**HTTP-трафик / код**

```
GET /orders  HTTP/1.1
Host: api.example
Authorization: Bearer eyJhbG…J9
Accept: application/json
```

#### Шаг 16. 6.2 · API проверяет токен и отвечает

**Что происходит**

API-ресурс выполняет проверку входящего access_token: (1) если токен JWT и API ≠ AS — подпись публичным ключом из JWKS AS (kid из заголовка); (2) iss == AS; (3) aud содержит identifier API (аудитория — «для кого выдан»); (4) exp > now; (5) scope покрывает операцию (GET /orders требует scope=orders:read). Всё совпало — 200 с данными. Любое несоответствие — 401 с заголовком WWW-Authenticate: Bearer error="invalid_token" (RFC 6750 §3): этот заголовок — стандартный способ сказать клиенту «токен невалиден, вот почему». error может быть invalid_token (подпись/exp/aud), insufficient_scope (не хватает scope), invalid_request. Клиент по 401 + WWW-Authenticate понимает: пора на refresh (шаг 7.1), а не показывать пользователю «ошибка». API НЕ обращается к AS на каждый запрос (если токен JWT) — всё локально по JWKS; это и есть производительность stateless-проверки.

**Подписи стрелок этого шага**

  • **API (ресурс)** (собственное действие): 6.2 подпись · aud · exp · scope
  • API (ресурс) → Приложение (РП): 200 OK · данные (JSON)

**Что делаете вы (реализация)**

- Проверка на КАЖДОМ эндпоинте: подпись + iss + aud + exp + scope
- 401 + WWW-Authenticate: Bearer error="invalid_token" (RFC 6750 §3)

**HTTP-трафик / код**

```
200 OK
Content-Type: application/json
{
 "orders": [
  {"id": 1001, "item": "…", "total": 1290 },
  {"id": 1002, "item": "…", "total": 450 } ]
}
// при сбое: 401
// WWW-Authenticate: Bearer error="invalid_token"
```

#### Шаг 17. 7.1 · Запрос обновления (refresh)

**Что происходит**

access_token живёт 300–3600 с (expires_in из шага 4.3). Приложение заранее (за 30 с до exp) или по 401 от API (шаг 6.2) инициирует refresh: POST /token с grant_type=refresh_token + refresh_token (из хранилища) + аутентификация клиента (private_key_jwt / mTLS). Это тот же endpoint и тот же канал, что и шаг 4.1 — server-to-server, без браузера, без пользователя. Критично: refresh_token — в body, не в query (как и любой токен). Автоматический retry — ОДНА попытка: если refresh вернул 400 (refresh_token expired/invalid) — это не «попробовать ещё раз», а «сессия мертва, нужен полный вход» (шаг 1.1). Зацикливание на refresh (retry loop) — классический баг: приложение бесконечно шлёт мёртвый refresh, пользователь видит спиннер. Правило: один refresh-запрос → 200 (новые токены) или 4xx (полный выход + «вход просрочен»).

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): 7.1 POST /token (grant_type=refresh_token)

**Что делаете вы (реализация)**

- Триггер: exp − 30 с (проактивно) ИЛИ 401 от API (реактивно); ОДНА попытка
- 4xx на refresh → полный выход + «вход просрочен»; не зацикливаться

**HTTP-трафик / код**

```
POST /token  HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Authorization: Bearer <JWT-assertion>

grant_type=refresh_token
&refresh_token=M42dG6…
```

#### Шаг 18. 7.2 · Новая пара токенов (rotation)

**Что происходит**

AS по валидному refresh_token выдаёт НОВУЮ пару: новый access_token + НОВЫЙ refresh_token, и старый refresh_token мгновенно АННУЛИРУЕТСЯ (rotation — ротация, обязательная по лучшей практике Auth 2.1). Приложение ЗАМЕНЯЕТ refresh_token в хранилище на новый ДО отправки следующего запроса (порядок: сохрани новый → потом работай). Старый refresh после ротации мёртв: если он вдруг придёт на /token повторно — это либо баг клиента (двойной запрос), либо атака (украденный старый refresh). AS фиксирует reuse: если refresh_token, который уже был ротирован, приходит снова — AS отзывает ВСЮ цепочку (все токены сессии, включая свежий), потому что либо клиент сломан, либо токен украден. Это «reuse detection» — та же логика, что и single-use для code (шаг 4.2). Пользователь не замечает ротацию: для него «я всё ещё вошёл». Для безопасности — каждый refresh сужает окно жизни украденного токена.

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Приложение (РП): 7.2 новый access + новый refresh (старый мёртв)

**Что делаете вы (реализация)**

- Замените refresh_token в хранилище ДО следующего запроса; старый — мёртв
- Reuse ротированного refresh → AS отзывает всю цепочку (см. вкладку Refresh-ротация)

**HTTP-трафик / код**

```
200 OK
{
 "access_token": "eyJhbG…NEW2",
 "refresh_token": "M42dG6…NEW2",
 "expires_in": 3600,
 "token_type": "Bearer" }
// старый refresh_token с этого момента невалиден
```

#### Шаг 19. 8.1 · Отзыв токенов (revoke)

**Что происходит**

Приложение (или пользователь — «выйти») вызывает RFC 7009: POST /revoke с token (refresh_token, который отзываем) + token_type_hint=refresh_token + аутентификация клиента. AS аннулирует токен: он больше не пройдёт на /token (refresh) и, если AT тоже в цепочке, — на API. Критичное поведение RFC 7009: AS отвечает 200 OK даже если токен уже невалиден или неизвестен — это намеренно, чтобы не раскрывать атакующему, существует ли токен. Поэтому 200 ≠ «точно отозвал», а «принято, проверять не будем». Порядок вызовов при выходе: revoke ДО очистки сессии приложения (если сначала очистить сессию — потеряем refresh_token и не сможем отозвать). Отзыв refresh_token ломает цепочку: после revoke нельзя refresh (шаг 7.1), и следующий вход — полный (шаг 1.1). access_token живёт до exp (если не отозван отдельно): по RFC 6750 resource server МОЖЕТ, но не обязан проверять отозванность AT на каждый запрос — на практике AT сгорит по exp (300–3600 с).

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): 8.1 POST /revoke (refresh_token)

**Что делаете вы (реализация)**

- POST /revoke: token + token_type_hint + client_auth; 200 даже на невалидный (RFC 7009)
- Порядок: revoke → потом чистить сессию приложения (иначе потеряете refresh)

**HTTP-трафик / код**

```
POST /revoke  HTTP/1.1
Content-Type: application/x-www-form-urlencoded
Authorization: Bearer <JWT-assertion>

token=M42dG6…
&token_type_hint=refresh_token
→ 200 OK (даже если токен неизвестен)
```

#### Шаг 20. 8.2 · Завершение сессии у AS (end_session)

**Что происходит**

После revoke (шаг 8.1) приложение завершает сессию на стороне AS — это Single Logout: пользователь выходит из приложения, и его сессия в AS тоже гаснет (иначе cookie AS живёт, и следующий вход на любое RP этого AS — без пароля). Механика: браузер делает GET на end_session_endpoint AS с id_token_hint (ID-токен, который AS выдал ЭТОМУ пользователю в ЭТОЙ сессии — AS по нему находит сессию) + post_logout_redirect_uri (куда вернуть браузер после — должен быть предзарегистрирован в AS, иначе AS не редиректит). AS гасит свою сессию (удаляет cookie as_session) и редиректит на post_logout_redirect_uri. Порядок с приложением: приложение чистит СВОЮ сессию (cookie) ДО редиректа на AS — иначе после возврата на app.example cookie приложения ещё жива, и пользователь «входит» мгновенно, хотя AS его уже выгнал. id_token_hint — именно из ТЕКУЩЕЙ сессии (не из кэша, не из другой): AS привязывает logout к конкретному ID-токену.

**Подписи стрелок этого шага**

  • Браузер → Сервер авторизации (АС): 8.2 GET /end-session?id_token_hint → сессия АС мёртва

**Что делаете вы (реализация)**

- GET end_session?id_token_hint={текущий}&post_logout_redirect_uri={зарегистрированный}
- Чистите cookie приложения ДО редиректа на AS; id_token_hint — из текущей сессии

**HTTP-трафик / код**

```
GET /end-session?id_token_hint=eyJhbG…QzI5
  &post_logout_redirect_uri=https://app.example/bye
→ AS: сессия AS уничтожена, cookie as_session удалена
→ 302 https://app.example/bye
```

| 2 | Приложение (РП) → Браузер: 302 /authorize?code_challenge=S256(…) |
| 3 | **Сервер авторизации (АС)** (собственное действие): сохранить challenge в сессию code |
| 4 ⚠ | Сервер авторизации (АС) → Браузер: 302 /callback?code=…<br>**Браузер** (собственное действие): ⚠ перехватчик видит code |

### Описание шагов

#### Шаг 1. Генерация пары verifier / challenge

**Что происходит**

Одно действие одного актора: приложение генерирует code_verifier — случайную строку 43–128 символов из алфавита [A-Z a-z 0-9 - . _ ~] (RFC 7636 §4.1, генерация только CSPRNG). Из него считается code_challenge = BASE64URL(ASCII(SHA256(ASCII(code_verifier)))) — детерминированно, один и тот же verifier всегда даёт один challenge. Это «двухполовинка»: verifier — секрет, остаётся на бэкенде; challenge — публичная хеш-«отпечатка», которую можно смело показать. Метод обязателен S256: plain (challenge = verifier) запрещён Auth 2.1, потому что в plain перехвативший challenge перехватил и сам секрет. Зачем: код (code) летит через браузер — незащищённый канал; PKCE делает его бесполезным без verifier.

**Подписи стрелок этого шага**

  • Браузер → Приложение (РП): «Войти»
  • **Приложение (РП)** (собственное действие): verifier = random(43–128), challenge = S256(verifier)

**Что делаете вы (реализация)**

- Генерация: 32 байта crypto.randomBytes → base64url (43 символа) — хватает и в verifier, и как энтропийный минимум RFC
- plain запрещён: method строго S256

**HTTP-трафик / код**

```
verifier  = DB7gj0s2kD-s41AroUIphRi7gD72JFPDTrNpT4U4JSU
challenge = BASE64URL(SHA256(verifier))
        = E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
```

#### Шаг 2. Challenge — в /authorize

**Что происходит**

Одно действие: приложение добавляет ДВА параметра к URL /authorize — code_challenge (публичная половинка) и code_challenge_method=S256. ВНИМАНИЕ: code_verifier в этот URL НЕ попадает — он уже лежит в серверной сессии (см. Основной вход, шаг 1.2). В URL-параметрах только то, что можно показать: challenge безопасен, потому что из него verifier не восстановить (SHA256 — односторонняя, 256 бит — перебор невозможен). Браузер может этот URL видеть, записывать в историю, слать в Referer — challenge от этого не теряет свойств. AS запомнит challenge и на этом шаге ещё ничего не проверяет: он просто фиксирует «для этого клиента, с этим redirect_uri, этот challenge заявлен».

**Подписи стрелок этого шага**

  • Приложение (РП) → Браузер: 302 /authorize?code_challenge=S256(…)

**Что делаете вы (реализация)**

- code_challenge + code_challenge_method=S256 — в query /authorize; verifier — только в сессии бэкенда

**HTTP-трафик / код**

```
GET /authorize?…&code_challenge=E9Melhoa2Owv…
  &code_challenge_method=S256
  (code_verifier в URL отсутствует)
```

#### Шаг 3. AS привязывает challenge к code

**Что происходит**

Одно действие: после входа пользователя и согласия AS генерирует одноразовый code и привязывает к нему challenge, который пришёл в /authorize. Привязка — в хранилище AS: {code, client_id, redirect_uri, challenge, nonce, exp}. С этого момента code «знает», какой challenge на него заявлен: обменять этот code можно будет только предъявив verifier, чей SHA256 совпадёт с challenge. Это и есть суть PKCE: код становится привязанным не только к клиенту (client_id), но и к «владельцу verifier». Пока пользователь ходил через браузер, challenge уже зафиксирован на стороне AS — перехватить код и обменять его без verifier нельзя.

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): сохранить challenge в сессию code

**Что делаете вы (реализация)**

- Храните привязку {code → challenge} до обмена; TTL 60–300 с

**HTTP-трафик / код**

```
AS: codes[code] = {
  challenge: "E9Melhoa2Owv…",
  client_id: "web-app-01",
  exp: now + 300s }
```

#### Шаг 4. Возврат code — и перехват в канале

**Что происходит**

Два события: (1) AS редиректит браузер на callback приложения с code + state — код оказывается в адресной строке; (2) ⚠ АТАКА: перехватчик (зловредный сайт на том же устройстве, кэш прокси, история браузера, Referer в логи) забирает этот code и пробует обменять его первым — до того, как честное приложение. Именно этот сценарий PKCE и закрывает: до Auth 2.0/PKCE перехватчик с кодом получал токены легально. Теперь у перехватчика есть code, но НЕТ verifier, а AS потребует его на обмене (шаг 6). Код живёт 60–300 секунд — окно атаки узкое, и оно закрыто.

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Браузер: 302 /callback?code=…
  • **Браузер** (собственное действие): ⚠ перехватчик видит code

**Что делаете вы (реализация)**

- Код в URL = публичная зона; безопасность держится не на «коде не должны увидеть», а на отсутствии verifier у сторонних

**HTTP-трафик / код**

```
⚠ перехватчик видит:
GET /callback?code=SplxlOBeZQQYbYS6WxSbIA&state=…
и пытается: POST /token (code=…, verifier=??? )
```

#### Шаг 5. Честный обмен: code + verifier

**Что происходит**

Одно действие: приложение бэкенда (server-to-server, TLS) шлёт POST /token с code И code_verifier из СВОЕЙ сессии. verifier приходит по закрытому каналу (бэкенд → AS), не через браузер, и AS получает его впервые. Приложение предъявляет code «открывающим ключом»: сам код — публичная половина, verifier — секретная. Если бы код уже поменял перехватчик (шаг 4) — он не сможет выполнить этот шаг: у него нет verifier.

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): POST /token (code + code_verifier)

**Что делаете вы (реализация)**

- POST /token: grant_type=authorization_code + code + code_verifier (из сессии, не из query)

**HTTP-трафик / код**

```
POST /token
grant_type=authorization_code
&code=SplxlOBeZQQYbYS6WxSbIA
&code_verifier=DB7gj0s2kD-s41…
```

#### Шаг 6. AS проверяет PKCE и выдаёт токены

**Что происходит**

Одно действие: AS вычисляет SHA256(verifier из запроса), кодирует в base64url и сравнивает с сохранённым challenge. Совпало — токены: 200 {access_token, id_token, refresh_token}. Не совпало (верификер чужой, отсутствует или битый) — 400 invalid_grant (RFC 7636 §4.6), и код сгорает. Проверка атомарна вместе с single-use: строка code удаляется при обмене. Если верификер не совпал, но code был «наш» — это признак атаки или бага: логировать как инцидент.

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): S256(verifier) == challenge?  ✓ → 200 токены

**Что делаете вы (реализация)**

- SHA256(verifier) == challenge → 200 + токены; иначе 400 invalid_grant (RFC 7636 §4.6)

**HTTP-трафик / код**

```
AS: base64url(sha256("DB7gj0…")) == "E9Melhoa2Owv…"? → да
→ 200 { access_token, id_token, refresh_token }
```

#### Шаг 7. Атака перехватчика: code без verifier

**Что происходит**

⚠ Итог атаки из шага 4: перехватчик добрался к /token со СВОИМ client-аутентификатором (если это публичный клиент с тем же client_id) и кодом, но предъявить verifier не может: (1) SHA256 переобратимо не восстановить (256 бит), (2) у него нет сессии приложения, где лежит verifier. AS отвечает 400 invalid_grant и код сгорает (single-use): честное приложение, даже придя позже с верным verifier, уже не обменяет — но это корректная защита, а не баг: приложение начнёт вход заново. Итог: украденный код бесполезен. Это и есть весь смысл PKCE в одном кадре.

**Подписи стрелок этого шага**

  • **Браузер** (собственное действие): ⚠ перехватчик шлёт code без verifier
  • **Сервер авторизации (АС)** (собственное действие): S256(?) != challenge → invalid_grant ✗

**Что делаете вы (реализация)**

- Поведение AS: без верного verifier — 400, код сгорает; приложение при 400 invalid_grant на обмене — полный повтор входа

**HTTP-трафик / код**

```
⚠ POST /token (code=SplxlO…, verifier=нет)
→ 400 { "error": "invalid_grant" }
код сгорел; честный обмен невозможен — повтор входа
```

## 3. Авторизация confidential-клиента — private_key_jwt и mTLS

### Участники диаграммы

| # | Участник |
|---|----------|
| 1 | Приложение (РП) |
| 2 | Сервер авторизации (АС) |
| 3 | Хранилище ключей |

### Подписи на стрелках переходов

| Шаг | Переход |
|-----|---------|
| 1 | **Приложение (РП)** (собственное действие): генерация пары ключей (RSA/EC), pub → JWKS<br>Приложение (РП) → Хранилище ключей: pub key → secret manager / client metadata |
| 2 | Приложение (РП) → Сервер авторизации (АС): POST /token + client_assertion=JWT (прив. ключ) |
| 3 | Сервер авторизации (АС) → Хранилище ключей: получить pub ключ клиента (jwks_uri) |
| 4 | **Сервер авторизации (АС)** (собственное действие): подпись ✓ · iss=sub=client_id · aud=/token · exp<10м · jti новый |
| 5 | Сервер авторизации (АС) → Приложение (РП): 200 токены (client auth пройден) |

### Описание шагов

#### Шаг 1. Генерация пары ключей вместо client_secret

**Что происходит**

Одно действие: при регистрации конфиденциального клиента в AS вместо симметричного client_secret генерируется АСИММЕТРИЧНАЯ пара: приватный ключ (никогда не покидает бэкенд приложения) и публичный. Публичный загружается в AS (в запись клиента: jwks_uri или jwks inline). Зачем: client_secret — симметричный секрет: любой, кто его увидит (лог, переменная окружения, инцидент на бэкенде), становится этим клиентом. При RSA/EC-паре украсть «доступ» через публичную часть нельзя: подпись делает только приватный ключ. Auth 2.1 (RFC 9700 §8) не рекомендует client_secret для серверных приложений, где есть надёжный способ аутентификации (ключ, mTLS).

**Подписи стрелок этого шага**

  • **Приложение (РП)** (собственное действие): генерация пары ключей (RSA/EC), pub → JWKS
  • Приложение (РП) → Хранилище ключей: pub key → secret manager / client metadata

**Что делаете вы (реализация)**

- Пара: EC P-256 (или RS 2048+); приватный — только в HSM/секрет-менеджере приложения
- Публичный — в AS: jwks_uri или jwks inline в записи клиента

**HTTP-трафик / код**

```
openssl ecparam -name prime256v1 -genkey -noout > client_priv.pem
openssl ec -in client_priv.pem -pubout > client_pub.pem
# client_pub → AS (jwks)
```

#### Шаг 2. JWT-assertion вместо client_secret

**Что происходит**

Одно действие: на каждом обращении к /token и /revoke приложение строит JWT-assertion (client assertion) и кладёт его в Authorization: Bearer <assertion>. Заголовок: {alg: ES256, typ: "JWT", kid: …}. Payload ОБЯЗАН содержать: iss = client_id, sub = client_id, aud = token_endpoint AS, exp (≤10 минут от подписания), iat. Подпись — приватным ключом клиента (SHA256 → ECDSA при ES256). Это «письмо-доверенность, подписанное личным ключом клиента»: AS видит не «пароль», а подписанный документ. TTL 10 минут — стандарт: assertion не должен жить, и повторное использование одной подписи через 10 минут = красный флаг (anti-replay).

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): POST /token + client_assertion=JWT (прив. ключ)

**Что делаете вы (реализация)**

- Claims: iss=sub=client_id, aud=token_endpoint, exp ≤ 10 мин, iat; подпись ES256/RS256
- Authorization: Bearer <JWT-assertion> вместо Basic/secret в body

**HTTP-трафик / код**

```
{
 "alg": "ES256", "typ": "JWT", "kid": "key-2026-11"
}
{
 "iss": "web-app-01", "sub": "web-app-01",
 "aud": "https://as.example/token",
 "exp": 1762362000, "iat": 1762359600
}
<подпись ECDSA-SHA256 приватным ключом>
```

#### Шаг 3. AS берёт публичный ключ клиента

**Что происходит**

Одно действие: AS получает assertion и берёт ПУБЛИЧНЫЙ ключ клиента — из записи клиента (jwks inline) или по jwks_uri, кэшируя (аналогично JWKS, вкладка «Проверка токена»). kid из заголовка JWT выбирает конкретный ключ (клиент может ротировать). Ключ не приходит «в запросе» — он из хранилища AS, загруженный при регистрации/обновлении клиента. Если kid не найден в JWKS — 401 invalid_client (и опционально один retry после refresh JWKS на случай ротации). Публичный ключ не секрет: его можно показать, а вот подписанный assertion — нет, потому что подпись не подделать без приватного ключа.

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Хранилище ключей: получить pub ключ клиента (jwks_uri)

**Что делаете вы (реализация)**

- JWKS клиента: из jwks inline или jwks_uri, с кэшем; выбор по kid
- Неизвестный kid → 401 (допустим один retry после обновления JWKS)

**HTTP-трафик / код**

```
AS: GET https://app.example/.well-known/jwks.json
→ { "keys": [{ "kid": "key-2026-11", "kty": "EC", … }] }
```

#### Шаг 4. Проверка JWT: подпись + claims + anti-replay

**Что происходит**

Одно действие (атомарно): AS проверяет assertion целиком: (1) подпись публичным ключом (по kid); (2) alg — белый список ES256/RS256, none отклонить; (3) iss == sub == client_id из запроса; (4) aud == token_endpoint; (5) exp/iat — живые, exp − iat ≤ 10 минут. Всё совпало — клиент аутентифицирован, запрос обрабатывается дальше (exchange, refresh, revoke). Любое отклонение — 401 invalid_client с error_description. Anti-replay: assertion с одним iat/exp не должен приниматься дважды (опционально: хранение отпечатка assertion на TTL). Ключевой эффект: secret не передаётся вообще — передаётся ДОКАЗАНИЕ владения приватным ключом.

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): подпись ✓ · iss=sub=client_id · aud=/token · exp<10м · jti новый

**Что делаете вы (реализация)**

- Проверки: подпись + alg-белый список + iss/sub/aud + exp/iat (окно ≤ 10 мин)
- 401 invalid_client; опционально — хранение отпечатка assertion для anti-replay

**HTTP-трафик / код**

```
AS: verify(assertion, pubKey(kid)) → ok
   iss == sub == "web-app-01"? → да
   aud == token_endpoint? → да
   exp > now, exp-iat ≤ 600s? → да
→ клиент аутентифицирован
```

#### Шаг 5. Альтернатива: mTLS (RFC 8705) без секрета и без JWT

**Что происходит**

Одно действие: вместо JWT-assertion клиент аутентифицируется САМ TLS-рукопожатием: бэкенд предъявляет клиентский сертификат, и AS сверяет его (subject/SAN) с client_id. Спецификация RFC 8705: в запросе /token добавляется client_assertion_type=urn:ietf:params:oauth:client-assertion-type:mtls_client_auth + client_assertion=<hash> (SHA256-хеш сертификата, base64url — для корреляции). Секретов нет: и симметричного, и подписного — доверие держится на PKI (сертификат выдан доверенным CA или проверен по цепочке AS). Плюсы: ноль «секретов к хранению», нулевые JWT-окна replay; минусы: инфраструктура сертификатов, ротация — через CA/ACME. Для on-prem и меж-сервисных сценариев — часто лучший выбор.

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Приложение (РП): 200 токены (client auth пройден)

**Что делаете вы (реализация)**

- Сертификат клиента: в HSM/кэше TLS; AS проверяет цепочку + subject → client_id
- RFC 8705: client_assertion_type=…:mtls_client_auth + client_assertion=base64url(SHA256(сертификат))

**HTTP-трафик / код**

```
POST /token (TLS + клиентский сертификат)
client_assertion_type=
  urn:ietf:params:oauth:client-assertion-type:mtls_client_auth
&client_assertion=P0A5Zk4…
→ AS: сертификат → subject CN=web-app-01 → ok
```

## 4. Refresh-ротация и обнаружение повторного использования

### Участники диаграммы

| # | Участник |
|---|----------|
| 1 | Приложение (РП) |
| 2 | Сервер авторизации (АС) |
| 3 | Злоумышленник |

### Подписи на стрелках переходов

| Шаг | Переход |
|-----|---------|
| 1 | Приложение (РП) → Сервер авторизации (АС): POST /token (refresh=R1)<br>Сервер авторизации (АС) → Приложение (РП): access=A2 + refresh=R2 (R1 мёртв) |
| 2 | **Приложение (РП)** (собственное действие): хранить R2, забыть R1 |
| 3 ⚠ | Злоумышленник → Сервер авторизации (АС): ⚠ украденный R1 снова на /token |
| 4 | **Сервер авторизации (АС)** (собственное действие): R1 в reuse-реестре → DETECTED: компрометация |
| 5 | **Сервер авторизации (АС)** (собственное действие): отозвать ВСЕ токены клиента (каскад)<br>Сервер авторизации (АС) → Приложение (РП): invalid_grant + сессия пользователя сбита |

### Описание шагов

#### Шаг 1. Первый refresh: R1 → R2 (rotation)

**Что происходит**

Одно действие: приложение шлёт POST /token с grant_type=refresh_token + refresh_token=R1. AS проверяет: R1 жив (не отозван, не истёк), клиент — тот, кому R1 выдан. Всё ок — AS выдаёт НОВУЮ пару: access_token (новый) и refresh_token=R2, и в том же атомарном действии АННУЛИРУЕТ R1 (маркировка used/rotated). Ротация — не опция, а обязательная практика Auth 2.1: каждый refresh «сдвигает» секрет, и окно жизни украденного R1 заканчивается в момент выдачи R2. Ответ 200 {access_token, refresh_token: R2, …}. Пользователь не замечает: сессия продолжается.

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): POST /token (refresh=R1)
  • Сервер авторизации (АС) → Приложение (РП): access=A2 + refresh=R2 (R1 мёртв)

**Что делаете вы (реализация)**

- Ротация обязательна: старый refresh аннулируется в момент выдачи нового
- Порядок AS: атомарно «выдать R2 + пометить R1 мёртвым» (одна транзакция)

**HTTP-трафик / код**

```
POST /token
grant_type=refresh_token&refresh_token=***
→ 200 { access_token: A2, refresh_token: R2 }
// R1 с этого момента невалиден
```

#### Шаг 2. RP хранит только свежий refresh

**Что происходит**

Одно действие: приложение ЗАМЕНЯЕТ refresh_token в хранилище: R2 записывается, R1 удаляется (не «остаётся рядом»). Критично: хранилище держит ОДИН актуальный refresh на сессию, и запись атомарна (нет окна «оба есть»). Откуда это берётся: если R1 физически остался где-то (кэш, лог, реплика БД с задержкой), приложение может случайно послать R1 повторно — и AS сочтёт это reuse (шаг 3), даже если это не атака, а баг репликации. Поэтому — один refresh на сессию, атомарная замена, и refresh никогда не пишется в логи (он токен, и в URL он тоже не появляется — только в body POST).

**Подписи стрелок этого шага**

  • **Приложение (РП)** (собственное действие): хранить R2, забыть R1

**Что делаете вы (реализация)**

- Атомарная замена в хранилище: R2 записан, R1 удалён; ровно один refresh на сессию
- Refresh — только в body POST; не в URL, не в логи, не в кэш-слои с задержкой

**HTTP-трафик / код**

```
storage.refreshToken(sessionId) = R2  // атомарно
// R1 в хранилище больше нет
```

#### Шаг 3. Атака: украденный R1 повторно

**Что происходит**

⚠ Одно событие: злоумышленник, у которого есть COPIЯ R1 (утёк через XSS на фронтенде, лог, дам БД, реплика), шлёт POST /token с grant_type=refresh_token + refresh_token=R1 — тот же запрос, что и у честного приложения на шаге 1. С точки зрения AS: приходит refresh, который УЖЕ ротирован (R1 → R2 на шаге 1). Это и есть сигнал компрометации: честный клиент после ротации R1 не использует (шаг 2), поэтому любое появление R1 — либо украденная копия, либо критический баг. AS на этом шаге ЕЩЁ НЕ выдаёт токены — он переходит в режим обнаружения (шаг 4). Поведение «просто отказать 400» — недостаточное: злоумышленник узнаёт, что R1 «уже использован», и не получает доказательств атаки.

**Подписи стрелок этого шага**

  • Злоумышленник → Сервер авторизации (АС): ⚠ украденный R1 снова на /token

**Что делаете вы (реализация)**

- Любое повторное использование ротированного refresh — сигнал компрометации, а не «просто ошибка»

**HTTP-трафик / код**

```
⚠ POST /token (злоумышленник)
grant_type=refresh_token&refresh_token=***
// AS: R1 уже ротирован в R2 → тревога
```

#### Шаг 4. Обнаружение: AS фиксирует компрометацию

**Что происходит**

Одно действие: AS выполняет reuse detection: помечает ВСЮ цепочку refresh-токенов сессии как скомпрометированную и отзывает: R2 (актуальный, у честного клиента), все доступные access_token сессии, и сам R1. Логика: мы не знаем, у кого R1, но знаем, что у НЕГО. А R2 у того, кто его получил, — а это может быть и тот же злоумышленник (если R1 украли и обменяли раньше, чем честный клиент). Поэтому отзывается ВСЁ: и «старое», и «новое». Записывается инцидент (timestamp, client_id, session, R1/R2 id) — для расследования. Это не «ошибка 400»: это событие безопасности.

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): R1 в reuse-реестре → DETECTED: компрометация

**Что делаете вы (реализация)**

- Reuse → отозвать ВСЮ цепочку: актуальный refresh + все access сессии + сам повторный токен
- Инцидент в SIEM: кто, когда, какой refresh повторили

**HTTP-трафик / код**

```
AS: reuse(R1) →
revoke(R2), revoke(access-токены сессии), mark(session=compromised)
log incident {t, client, session, tokens:[R1,R2,A2]}
```

#### Шаг 5. Итог: и злоумышленник, и честный клиент — вне

**Что происходит**

Два исхода из шага 4: (1) злоумышленник получил 400 invalid_grant (R1 мёртв, цепочка мёртва); (2) честное приложение при следующем запросе получит 401 от API (access отозван) → попытка refresh → R2 тоже мёртв → 400 → полное завершение сессии, пользователь видит «вход просрочен, войдите снова». Итог: ни одна сторона с украденным refresh-токеном не работает дальше. Стоимость для честного пользователя — один повторный вход (и MFA, если включена). Стоимость для атакующего — нулевой доход: токены мёртвы, а след в SIEM есть. Это и есть «reuse detection + каскадный отзыв» — защита уровня сессии, а не токена.

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): отозвать ВСЕ токены клиента (каскад)
  • Сервер авторизации (АС) → Приложение (РП): invalid_grant + сессия пользователя сбита

**Что делаете вы (реализация)**

- Честный клиент: 401 API → refresh 400 → полный выход + «вход просрочен» (без retry-loop)
- Инцидент: один повторный вход для пользователя vs. нулевой доход для атакующего

**HTTP-трафик / код**

```
честный: GET /orders → 401
 → POST /token (R2) → 400 invalid_grant
 → сессия завершена, «Войдите снова»
⚠ атакующий: 400 invalid_grant (R1 мёртв)
```

## 5. DPoP — токен, привязанный к ключу предъявителя

### Участники диаграммы

| # | Участник |
|---|----------|
| 1 | Приложение (РП) |
| 2 | Сервер авторизации (АС) |
| 3 | API (ресурс) |
| 4 | Злоумышленник |

### Подписи на стрелках переходов

| Шаг | Переход |
|-----|---------|
| 1 | **Приложение (РП)** (собственное действие): DPoP-ключ: EC P-256 (jkt = thumbprint) |
| 2 | Приложение (РП) → Сервер авторизации (АС): POST /token + header DPoP: proof{htu,htm,jti,ath=S256(code)} |
| 3 | **Сервер авторизации (АС)** (собственное действие): proof ✓ · ath=S256(code) ✓ · jkt из pub key в proof<br>Сервер авторизации (АС) → Приложение (РП): access_token (token_type: DPoP, cnf.dpop_jkt=jkt) |
| 4 | Приложение (РП) → API (ресурс): GET /orders + Authorization: DPoP <AT> + DPoP: proof{htu,htm,jti} |
| 5 | **API (ресурс)** (собственное действие): подпись proof ✓ · jkt == cnf.dpop_jkt ✓ → 200 |
| 6 ⚠ | Злоумышленник → API (ресурс): ⚠ украденный AT + СВОЙ proof (чужой jkt)<br>**API (ресурс)** (собственное действие): jkt ≠ cnf.dpop_jkt → 401 ✗ |

### Описание шагов

#### Шаг 1. DPoP-ключ клиента

**Что происходит**

Одно действие: приложение генерирует АСИММЕТРИЧНУЮ пару (EC P-256 или RS2048) — это DPoP-ключ, который делает access_token привязанным к конкретному отправителю (sender-constrained). Публичная часть — в JWT «proof of possession» (DPoP proof), который приложение будет подписывать к каждому запросу. Ключ НЕ загружается в AS как jwks (в отличие от client keys, вкладка «Авторизация клиента»): AS видит его только внутри proof, в поле jkt (Thumbprint — SHA256-отпечаток DER публичного ключа, base64url, RFC 7638). Зачем: access_token по-прежнему «бумажка, которую можно перехватить» — DPoP делает её бесполезной без КЛЮЧА: токен и ключ — две половины одной пары.

**Подписи стрелок этого шага**

  • **Приложение (РП)** (собственное действие): DPoP-ключ: EC P-256 (jkt = thumbprint)

**Что делаете вы (реализация)**

- Пара EC P-256 (или RS 2048); приватный — в HSM приложения
- jkt = base64url(SHA256(DER публичного ключа)) — RFC 7638; ключ не загружается в AS как JWKS

**HTTP-трафик / код**

```
genkey pair (P-256) → priv, pub
jkt = base64url(sha256(DER(pub))) = "16a0…de0c"
// priv — в HSM; pub — только внутри proof
```

#### Шаг 2. Proof на /token: привязка к code через ath

**Что происходит**

Одно действие: при обмене code на /token приложение строит DPoP proof (JWT) и кладёт его в заголовок DPoP: <proof>. Proof обязателен содержать: jti (уникальный, anti-replay), iat, htu (target URI — token_endpoint), htm (HTTP-метод — POST), ath (Authorization Request Hash — base64url(SHA256(ASCII(«канонического» URL-запроса /authorize с code в query))) — RFC 9449 §4.2). Подпись — DPoP-ключом (ES256). ath — это «привязка» proof к конкретному code-запросу: proof, подписанный для одного /authorize, не сработает для другого. Клиент также шлёт HTTP-заголовок DPoP-Nonce (если AS его вернул в 401) — дополнительный anti-replay.

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): POST /token + header DPoP: proof{htu,htm,jti,ath=S256(code)}

**Что делаете вы (реализация)**

- Proof: jti + iat + htu + htm + ath; подпись DPoP-ключом (ES256)
- ath = base64url(SHA256(канонический /authorize URL с code)) — RFC 9449 §4.2
- Заголовок: DPoP: <proof> (отдельно от Authorization)

**HTTP-трафик / код**

```
DPoP: eyJhbG…<proof>
claims: { jti: "u1k2…", iat: 1762360000,
  htu: "https://as.example/token",
  htm: "POST",
  ath: "jH2l…",  // SHA256(/authorize?…&code=SplxlO…)
  jkt: "16a0…de0c" }
+ Authorization: Bearer <JWT-assertion> (client auth)
```

#### Шаг 3. AS валидирует proof и выдаёт sender-constrained токен

**Что происходит**

Одно действие: AS проверяет proof: (1) подпись публичным ключом (из proof, по jkt); (2) htu == token_endpoint, htm == POST; (3) ath == SHA256(code-запроса, который AS обрабатывает); (4) jti не повторен (anti-replay). Всё ок — AS выдаёт токены, и access_token получает claim cnf = { "dpop_jkt": "16a0…de0c" } — привязку к DPoP-ключу. С этого момента access_token — не «просто JWT с claims», а «JWT, который работает только при предъявлении proof с jkt=16a0…de0c». refresh_token — не привязывается (он и так на бэкенде, и proof на /token тоже шлётся). Итог: даже перехватив access_token, атакующий не предъявит к нему proof (нет приватного DPoP-ключа).

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): proof ✓ · ath=S256(code) ✓ · jkt из pub key в proof
  • Сервер авторизации (АС) → Приложение (РП): access_token (token_type: DPoP, cnf.dpop_jkt=jkt)

**Что делаете вы (реализация)**

- CNF-claim: cnf.dpop_jkt = jkt из proof
- Проверки proof: подпись + htu/htm + ath + jti (anti-replay)

**HTTP-трафик / код**

```
200 OK
{
 "access_token": "eyJhbG…cnf…",
  // payload: { …, "cnf": { "dpop_jkt": "16a0…de0c" } },
 "refresh_token": "M42dG6…",
 "expires_in": 3600 }
```

#### Шаг 4. Запрос к RS: токен + свежий proof

**Что происходит**

Одно действие: приложение делает GET /orders к API с ДВУМЯ заголовками: (1) Authorization: Bearer <access_token> — как обычно (RFC 6750); (2) DPoP: <новый proof> — подписанный DPoP-ключом, с htu=/orders, htm=GET, jti (новый, не из /token). Proof НЕ переиспользуется: на каждый запрос — новый jti, iat. ath здесь НЕ нужен (это не /token-обмен) — он нужен только для привязки к code. API не знает, «что это за proof» до проверки — для API это ещё один заголовок. Ключевой момент: access_token и proof — ДВЕ РАЗНЫЕ ВЕЩИ: токен — права, proof — доказательство владения ключом. У атакующего может быть токен, но не будет proof.

**Подписи стрелок этого шага**

  • Приложение (РП) → API (ресурс): GET /orders + Authorization: DPoP <AT> + DPoP: proof{htu,htm,jti}

**Что делаете вы (реализация)**

- Каждый запрос: Authorization: Bearer <AT> + DPoP: <новый proof (jti, iat, htu, htm)>
- Proof не переиспользуется: новый jti на каждый запрос

**HTTP-трафик / код**

```
GET /orders
Authorization: Bearer eyJhbG…cnf…
DPoP: eyJhbG…<proof>
claims: { jti: "x9p2…", iat: 1762360030,
  htu: "https://api.example/orders",
  htm: "GET",
  jkt: "16a0…de0c" }
```

#### Шаг 5. RS: jkt == cnf.dpop_jkt — 200

**Что происходит**

Одно действие: API проверяет: (1) access_token валиден (подпись, iss, aud, exp — как в Основном входе шаг 6.2); (2) НОВОЕ: cnf.dpop_jkt из access_token == jkt из proof — «ключ, которым подписан proof, тот самый, к которому привязан токен»; (3) proof подписан публичным ключом из jkt; (4) htu == URL запроса, htm == метод; (5) jti не повторен. Всё совпало — 200 с данными. Если cnf.dpop_jkt != jkt — 401 invalid_token: «токен привязан к другому ключу». Это и есть sender-constrained проверка: токен и ключ — неразделимая пара.

**Подписи стрелок этого шага**

  • **API (ресурс)** (собственное действие): подпись proof ✓ · jkt == cnf.dpop_jkt ✓ → 200

**Что делаете вы (реализация)**

- Проверка RS: AT валиден + cnf.dpop_jkt == jkt(proof) + подпись proof + htu/htm + jti
- Несоответствие jkt → 401 invalid_token

**HTTP-трафик / код**

```
API: AT ok (подпись/iss/aud/exp)
    cnf.dpop_jkt == "16a0…de0c"? → да
    proof.jkt == "16a0…de0c"? → да
    sig(proof, pub(jkt)) ok? → да
→ 200 { "orders": […] }
```

#### Шаг 6. Атака: украденный AT без DPoP-ключа

**Что происходит**

⚠ Итог: атакующий перехватывает access_token (в логах, кэше, референсере) и шлёт GET /orders с Authorization: Bearer <украденный AT>. Но: (1) у него нет DPoP-ключа (он в HSM приложения), (2) он не может подписать proof с jkt, соответствующим cnf.dpop_jkt. Варианты: (a) без заголовка DPoP — API требует proof (401, если AT имеет cnf); (b) со СВОИМ proof (своё jkt) — cnf.dpop_jkt != jkt → 401 invalid_token; (c) подделать подпись — невозможно без приватного ключа. Итог: украденный access_token бесполезен — это и есть цель DPoP (RFC 9449): «токен без ключа = мёртвый».

**Подписи стрелок этого шага**

  • Злоумышленник → API (ресурс): ⚠ украденный AT + СВОЙ proof (чужой jkt)
  • **API (ресурс)** (собственное действие): jkt ≠ cnf.dpop_jkt → 401 ✗

**Что делаете вы (реализация)**

- Атакующий с AT, но без DPoP-ключа: 401 в любом из трёх вариантов (нет proof / чужой jkt / поддельная подпись)

**HTTP-трафик / код**

```
⚠ GET /orders
Authorization: Bearer <украденный AT>
DPoP: <чужой proof, jkt="ff99…">  // не тот
→ 401 { "error": "invalid_token" }
   // cnf.dpop_jkt != jkt(proof)
```

## 6. Device Flow — вход с устройства без браузера

### Участники диаграммы

| # | Участник |
|---|----------|
| 1 | Устройство (CLI / ТВ) |
| 2 | Сервер авторизации (АС) |
| 3 | Браузер |
| 4 | Пользователь |

### Подписи на стрелках переходов

| Шаг | Переход |
|-----|---------|
| 1 | Устройство (CLI / ТВ) → Сервер авторизации (АС): POST /device_authorization (client_id, scope)<br>Сервер авторизации (АС) → Устройство (CLI / ТВ): device_code · user_code=ABCD-EFGH · interval=5 |
| 2 | Пользователь → Браузер: ввести ABCD-EFGH на verification_uri<br>**Сервер авторизации (АС)** (собственное действие): ждём confirmation (TTL ~10 мин) |
| 3 | Устройство (CLI / ТВ) → Сервер авторизации (АС): POST /token (device_code) — поллинг раз в interval<br>Сервер авторизации (АС) → Устройство (CLI / ТВ): 400 authorization_pending — ещё ждём |
| 4 ⚠ | **Пользователь** (собственное действие): ⚠ polling чаще, чем interval<br>Устройство (CLI / ТВ) → Сервер авторизации (АС): POST /token (device_code)<br>Сервер авторизации (АС) → Устройство (CLI / ТВ): 400 slow_down — увеличить интервал |
| 5 ⚠ | Браузер → Сервер авторизации (АС): ⚠ user_code НЕ тем аккаунтом / отказ<br>Сервер авторизации (АС) → Устройство (CLI / ТВ): 400 user_denied / wrong_user / expired_token — стоп |
| 6 | **Сервер авторизации (АС)** (собственное действие): подтверждено → токены<br>Сервер авторизации (АС) → Устройство (CLI / ТВ): 200 access + refresh (device_code одноразовый) |

### Описание шагов

#### Шаг 1. Запрос device-авторизации

**Что происходит**

Одно действие: устройство без браузера (CLI, ТВ, IoT) шлёт POST на device_authorization_endpoint AS: client_id (и аутентификация клиента, если конфиденциальный) + scope. Ответ — 200 с ТРЁМ значениями: device_code (код для подтверждения — держит устройство, НО его показывают/вводят с другого устройства… точнее — устройство показывает user_code), user_code (короткий человекочитаемый код, который пользователь введёт в браузере на другом устройстве, формат XXXX-XXXX), verification_uri (https://as.example/activate — куда пойти), verification_uri_complete (с user_code в query — если AS поддерживает), expires_in (обычно 600 с), interval (минимальный период поллинга, обычно 5 с). Зачем flow: нет браузера на устройстве → нет callback → код «подтверждают» извне. Критично: user_code показываемому человеку, device_code — только устройству и AS; device_code НИКОГДА не показывается пользователю (он длинный, и его ввод в браузер — риск).

**Подписи стрелок этого шага**

  • Устройство (CLI / ТВ) → Сервер авторизации (АС): POST /device_authorization (client_id, scope)
  • Сервер авторизации (АС) → Устройство (CLI / ТВ): device_code · user_code=ABCD-EFGH · interval=5

**Что делаете вы (реализация)**

- Ответ: device_code (устройству) + user_code (человеку) + verification_uri + expires_in + interval
- device_code не показывать пользователю; user_code — короткий, формат XXXX-XXXX

**HTTP-трафик / код**

```
POST /device_authorization
client_id=tv-app-01&scope=openid+profile
→ 200 {
 "device_code": "GSArRw…",
 "user_code": "ABCD-2345",
 "verification_uri": "https://as.example/activate",
 "verification_uri_complete": "…/activate?code=ABCD-2345",
 "expires_in": 600,
 "interval": 5 }
```

#### Шаг 2. Пользователь подтверждает на втором устройстве

**Что происходит**

Два действия (пользователь + AS): (1) человек открывает verification_uri на ТЕЛЕФОНЕ/НОУТБУКЕ и вводит user_code; (2) AS проверяет user_code (он жив — не истёк, не использован), запускает вход: сессия? нет → форма логина + MFA (обязательно, потому что вход идёт с НОВОГО устройства, доверие не переносится). После успешной аутентификации AS помечает device_code как approved (не выдаёт токены сразу — устройство их ещё не запросило). Устройство на этом шаге Ничего не делает: оно ждёт и опрашивает (шаг 3). Состояние «approved» существует у AS, и только подтверждённый user_code + device_code пара даст токены.

**Подписи стрелок этого шага**

  • Пользователь → Браузер: ввести ABCD-EFGH на verification_uri
  • **Сервер авторизации (АС)** (собственное действие): ждём confirmation (TTL ~10 мин)

**Что делаете вы (реализация)**

- Вход с нового устройства = полная аутентификация (MFA по политике AS)
- AS помечает device_code=approved; токены ещё НЕ выдаёт

**HTTP-трафик / код**

```
браузер (телефон): GET https://as.example/activate
→ введите код: ABCD-2345
→ логин + MFA → 200 «Готово, можно закрыть»
AS: device_code(GSArRw…) = approved
```

#### Шаг 3. Поллинг: device_code на /token

**Что происходит**

Одно действие (цикл): устройство каждые `interval` секунд (5 с из ответа) шлёт POST /token: grant_type=urn:ietf:params:oauth:grant-type:device_code + device_code + client_id (+ аутентификация клиента). AS отвечает по одной из четырёх: (1) authorization_pending — «ещё не подтвердили, ждите» (устройство ждёт interval и повторяет); (2) slow_down — «часто опрашивает» (устройство ждёт interval+5); (3) expired_token — device_code истёк (600 с прошло без подтверждения) — стоп, начать заново; (4) 200 с токенами — подтверждение произошло. Это единственный flow, где «ответ = продолжить ждать» является нормой: authorization_pending НЕ ошибка. Поллинг — по interval, не «как можно чаще»: AS следит (slow_down).

**Подписи стрелок этого шага**

  • Устройство (CLI / ТВ) → Сервер авторизации (АС): POST /token (device_code) — поллинг раз в interval
  • Сервер авторизации (АС) → Устройство (CLI / ТВ): 400 authorization_pending — ещё ждём

**Что делаете вы (реализация)**

- Поллинг строго по interval; authorization_pending — норма, не ошибка; stopped на expired_token
- Три стоп-состояния: expired_token, wrong_user, user_denied — дальше не опрашивать

**HTTP-трафик / код**

```
POST /token
client_id=tv-app-01
&grant_type=urn:ietf:params:oauth:grant-type:device_code
&device_code=GSArRw…
→ 400 { "error": "authorization_pending" }
   // ждём interval=5s → повтор
```

#### Шаг 4. Сбой: слишком частый поллинг → slow_down

**Что происходит**

Одно действие: устройство шлёт поллинг чаще, чем interval (например, каждый 1 с — «чтобы быстрее»). AS отвечает slow_down — это НЕ ошибка, а регулировка: устройство обязано увеличить паузу до interval + 5 с (10 с) и продолжать. Зачем: device flow — единственный, где «опрашивать до успеха» заложен в протокол, и без slow_down устройство бы молотило /token с частотой 1 req/s, а с тысячами устройств — DoS на самый уязвимый endpoint. Поведение устройства: при slow_down — пауза 10 с, затем normal. Если slow_down повторяются — устройство «сломано» (interval не читает): логировать. Это единственный «сбой» в flow, который исправляется увеличением паузы, а не повтором входа.

**Подписи стрелок этого шага**

  • **Пользователь** (собственное действие): ⚠ polling чаще, чем interval
  • Устройство (CLI / ТВ) → Сервер авторизации (АС): POST /token (device_code)
  • Сервер авторизации (АС) → Устройство (CLI / ТВ): 400 slow_down — увеличить интервал

**Что делаете вы (реализация)**

- slow_down → пауза interval+5 (10 с) → продолжить; это регулировка, не ошибка

**HTTP-трафик / код**

```
POST /token (device_code, слишком часто)
→ 400 { "error": "slow_down" }
// устройство: sleep(10s) → повтор
```

#### Шаг 5. Сбой: wrong_user / user_denied

**Что происходит**

Два терминальных исхода (устройство перестаёт опрашивать): (1) user_denied — пользователь открыл verification_uri, ввёл user_code, но нажал «Отклонить» (не разрешил доступ). (2) wrong_user — пользователь подтвердил кодом, но вошёл в AS под ДРУГОЙ учёткой, чем та, к которой device_code «привязан» по политике (например, tenant-привязка: device_code выдан для tenant A, пользователь вошёл в tenant B). Оба — 400 с конкретным error, и устройство останавливает поллинг: повтор с тем же device_code бесполезен (он уже «сгорел» в терминальном состоянии). Что делает устройство: показывает «Доступ не разрешён» (user_denied) или «Неправильный аккаунт — попробуйте снова» (wrong_user) и предлагает начать заново (новый device_code).

**Подписи стрелок этого шага**

  • Браузер → Сервер авторизации (АС): ⚠ user_code НЕ тем аккаунтом / отказ
  • Сервер авторизации (АС) → Устройство (CLI / ТВ): 400 user_denied / wrong_user / expired_token — стоп

**Что делаете вы (реализация)**

- user_denied / wrong_user → стоп поллинга; новое device_code при повторе

**HTTP-трафик / код**

```
POST /token (device_code)
→ 400 { "error": "access_denied" }  // user_denied
→ 400 { "error": "authorization_pending",
        "error_description": "wrong account" } // wrong_user
// устройство: стоп, показать причину, «Повторить?»
```

#### Шаг 6. Успех: токены, device_code сгорел

**Что происходит**

Одно действие: AS подтверждает (шаг 2), устройство опрашивает (шаг 3) → AS отвечает 200 с токенами (access, id, refresh — как в Основном входе 4.3). Атомарно с выдачей AS АННУЛИРУЕТ device_code: повторный поллинг с ним → expired_token (code single-use, как authorization code). Устройство: (1) сохраняет токены (HttpOnly/шифрованное хранилище); (2) проверяет id_token (подпись, iss, aud, exp, nonce — но в device flow nonce обычно нет, т.к. нет /authorize-запроса: проверяйте sub + auth_time); (3) стоп поллинга, работа с API. Окно «подтвердил, но устройство не забрало» закрыто expires_in: если устройство не пришло за 600 с — device_code мёртв, подтверждение не выдаст токенов никому.

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): подтверждено → токены
  • Сервер авторизации (АС) → Устройство (CLI / ТВ): 200 access + refresh (device_code одноразовый)

**Что делаете вы (реализация)**

- 200 + токены → device_code мёртв (single-use); id_token проверить (sub, auth_time); стоп поллинга

**HTTP-трафик / код**

```
POST /token (device_code)
→ 200 { "access_token": "…", "id_token": "…",
        "refresh_token": "…", "expires_in": 3600 }
AS: device_code(GSArRw…) = consumed
// повтор: 400 expired_token
```

## 7. Step-Up (RFC 9470) — повторная аутентификация с MFA

### Участники диаграммы

| # | Участник |
|---|----------|
| 1 | Браузер |
| 2 | Приложение (РП) |
| 3 | Сервер авторизации (АС) |
| 4 | API (ресурс) |

### Подписи на стрелках переходов

| Шаг | Переход |
|-----|---------|
| 1 ⚠ | API (ресурс) → Браузер: GET /sensitive-op<br>**Браузер** (собственное действие): ⚠ require_step_up=true в /authorize |
| 2 | Браузер → Сервер авторизации (АС): GET /authorize?prompt=login&max_age=0&require_step_up=true |
| 3 | **Сервер авторизации (АС)** (собственное действие): MFA: TOTP / push / hardware key |
| 4 | Сервер авторизации (АС) → Браузер: 302 /callback?code=… (id_token с auth_time, acr) |
| 5 | **Браузер** (собственное действие): проверить: auth_time свежий? acr ∈ {s256, s356}?  ✓<br>Приложение (РП) → API (ресурс): Authorization: Bearer <AT> (scope includes sensitive) |

### Описание шагов

#### Шаг 1. Требование step-up: приложение требует MFA

**Что происходит**

Одно действие: приложение запрашивает у AS усиление: на обычном «я в сессии» запросе (например, запуск /authorize для чувствительной операции) приложение добавляет prompt=login (или require_max_age=300 — «аутентификации должно быть не больше 5 минут», или prompt=select_account для переключения). Механика: AS видит, что обычная сессия (password-только) НЕДОСТАТОЧНА для запрошенного уровня → запускает step-up: MFA-фактор (TOTP/SMS/push) поверх живой сессии. Зачем отдельно от полного входа: пользователь уже вошёл (пароль) — заставлять повторять логин не нужно, НО для «вывести 100 000» нужно доказать, что это человек, а не сессия, украденная через XSS. step-up = «докажи ещё раз, но только MFA-фактором». Результат step-up виден в ID-токене: amr (methods: ["pwd","mfa"]) и acr (level), и auth_time обновляется.

**Подписи стрелок этого шага**

  • API (ресурс) → Браузер: GET /sensitive-op
  • **Браузер** (собственное действие): ⚠ require_step_up=true в /authorize

**Что делаете вы (реализация)**

- prompt=login / require_max_age=N — «требуется свежая/усиленная аутентификация»
- Результат — в ID-токене: amr (pwd, mfa), acr (уровень), auth_time (обновлён)

**HTTP-трафик / код**

```
GET /authorize?…&prompt=login&require_max_age=300
// AS: сессия есть (pwd), но step-up (mfa) требуется
```

#### Шаг 2. AS запрашивает MFA

**Что происходит**

Одно действие: AS показывает MFA-шаг поверх СУЩЕСТВУЮЩЕЙ сессии: «Подтвердите TOTP-код / Push-уведомление». Пользователь подтверждает. AS: (1) обновляет сессию — добавляет mfa в список методов (amr: pwd+mfa), обновляет auth_time (или mfa_time — отдельный клейм); (2) повышает acr сессии до уровня, требующего MFA. Пароль НЕ запрашивается снова: сессия «парольная» уже есть, добавляется «MFA-слой». Это и есть step-up, а не полный вход: один фактор (MFA), не два (password+MFA). После step-up сессия AS — «усиленная»: любые /authorize с require_max_age=300 пройдут без повторного MFA в пределах окна. Если MFA не подтвердили (таймаут, 3 ошибки кода) — access_denied, sессия остаётся «неусиленной».

**Подписи стрелок этого шага**

  • Браузер → Сервер авторизации (АС): GET /authorize?prompt=login&max_age=0&require_step_up=true

**Что делаете вы (реализация)**

- MFA поверх сессии (не password+MFA); amr += mfa, auth_time обновлён
- Таймаут/3 ошибки кода → access_denied; сессия неусиленной

**HTTP-трафик / код**

```
AS: [MFA-экран] введите 6-значный код
→ TOTP ok
session.amr = ["pwd","mfa"]; session.auth_time = now
session.acr = "urn:mfa"
```

#### Шаг 3. Валидация step-up на стороне RP

**Что происходит**

Одно действие: приложение ПОЛУЧИЛО ID-токен после /authorize и ПРОВЕРЯЕТ, что step-up реально произошёл: (1) amr содержит "mfa" (не только "pwd"); (2) auth_time (или mfa_time) — свежий (в пределах require_max_age); (3) acr — уровень, который приложение требует для ЭТОЙ операции. Проверка на стороне RP ОБЯЗАТЕЛЬНА: AS может быть настроен «мягко» (step-up не требовать), и тогда ответственность на RP. Если amr=_pwd-only при требовании MFA — операция ЗАПРЕЩЕНА: 403 + «Требуется подтверждение». Критично: step-up — это свойство СЕССИИ AS + требования RP, и проверять «свежесть» должен RP: AS не обязан помнить, для какой операции был step-up (AS не знает, что «это вывод денег»).

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): MFA: TOTP / push / hardware key

**Что делаете вы (реализация)**

- RP проверяет amr⊇mfa + auth_time ≤ require_max_age + acr ≥ требуемый
- Не совпало → 403 + «требуется подтверждение» (не «ошибка»)

**HTTP-трафик / код**

```
const ok = payload.amr.includes("mfa")
  && (now - payload.auth_time) <= 300;
if (!ok) return 403 { "error": "step_up_required" };
```

#### Шаг 4. Работа с привилегированными операциями

**Что происходит**

Одно действие: операция с проверенным step-up выполняется (например, вывод средств, изменение email, удаление аккаунта). Приложение привязывает ПОЛИТИКУ step-up к операциям, а не к сессии: «чтение профиля — достаточно pwd; смена email — pwd+mfa ≤ 5 мин; вывод — pwd+mfa ≤ 60 с». Механика: перед привилегированным действием приложение сверяет ID-токен/сессию с политикой: достаточно свежий MFA? да → операция; нет → новый /authorize с require_max_age=N (шаг 1) → MFA (шаг 2) → операция. Пользователь видит: «Подтвердите, чтобы продолжить» — без полного пере-входа. Это UX-выигрыш step-up: не «выйдите и войдите снова с MFA», а «подтвердите одним фактором». Окна (300 с / 60 с) — политика приложения, не AS: AS только «отвечает» на require_max_age.

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Браузер: 302 /callback?code=… (id_token с auth_time, acr)

**Что делаете вы (реализация)**

- Политика per-операция: чтение — pwd; смена email — mfa ≤ 300s; вывод — mfa ≤ 60s
- Недостаточно → /authorize с require_max_age (не полный пере-вход)

**HTTP-трафик / код**

```
policy["withdraw"] = { amr: ["pwd","mfa"], max_age: 60 };
// проверка перед операцией:
if (now - session.mfa_time > 60) → step-up (шаг 1)
```

#### Шаг 5. Исход step-up: когда MFA НЕ требуется

**Что происходит**

Два исхода (симметрия шага 3): (1) amr содержит mfa И auth_time свежий (в пределах require_max_age) → операция выполняется БЕЗ повторного MFA (пользователь не видит запрос — step-up уже есть). (2) Сессия вообще без MFA, НО операция — низкорисковая (чтение профиля, просмотр заказов) → MFA не требуется: amr=pwd достаточно, require_max_age не ставится. Критично: step-up — НЕ «MFA на всё». Политика: низкий риск — pwd; средний — mfa ≤ 300s; высокий — mfa ≤ 60s. Если требовать MFA на каждый клик — пользователь отключит 2FA (реальный сценарий: friction → disable). Метрика: доля операций с step-up vs. без — если > 30% — политика слишком жёсткая, UX деградирует.

**Подписи стрелок этого шага**

  • **Браузер** (собственное действие): проверить: auth_time свежий? acr ∈ {s256, s356}?  ✓
  • Приложение (РП) → API (ресурс): Authorization: Bearer <AT> (scope includes sensitive)

**Что делаете вы (реализация)**

- МFA НЕ требуется: (a) свежий step-up есть; (b) операция низкорисковая
- Политика по рискам: pwd / mfa≤300s / mfa≤60s; не «MFA на всё»

**HTTP-трафик / код**

```
GET /profile (чтение) → amr=pwd достаточно → 200
GET /orders (средний) → mfa ≤ 300s? → да → 200
POST /withdraw (высокий) → mfa ≤ 60s? → нет → step-up
```

## 8. Выход — RP-Initiated Logout и Back-Channel Logout

### Участники диаграммы

| # | Участник |
|---|----------|
| 1 | Приложение A (РП) |
| 2 | Сервер авторизации (АС) |
| 3 | Приложение B (РП) |
| 4 | Браузер |

### Подписи на стрелках переходов

| Шаг | Переход |
|-----|---------|
| 1 | Браузер → Приложение A (РП): login → 302 /callback (sid=S-1 в IDT)<br>**Приложение A (РП)** (собственное действие): сессия: sid=S-1 (httpOnly cookie) |
| 2 | Приложение A (РП) → Сервер авторизации (АС): GET /session?sid=S-1 (session-check)<br>**Сервер авторизации (АС)** (собственное действие): sid жива? ✓ (или logout URL в body) |
| 3 | Браузер → Приложение A (РП): GET /logout (пользователь кликнул «Выйти»)<br>Приложение A (РП) → Сервер авторизации (АС): end_session_endpoint?id_token_hint&post_logout&state |
| 4 | Сервер авторизации (АС) → Браузер: 302 post_logout_redirect_uri (чистый браузер) |
| 5 ⚠ | Сервер авторизации (АС) → Приложение B (РП): ⚠ back-channel: POST { sid, sub } на logout_uris<br>**Приложение B (РП)** (собственное действие): сверка sig/sid/sub → уничтожить свою сессию |

### Описание шагов

#### Шаг 1. Сессия со sid: одна личность, один идентификатор

**Что происходит**

Одно действие: AS выдаёт ID-токен, и в нём — claim sid (session ID, RFC 7800 / OIDC Session Management). sid — уникальный идентификатор СЕССИИ AS (не пользователя, не токена): одна вошедшая личность в один момент = один sid. Все ID-токены, выданные в рамках этой сессии (любому RP), содержат ОДИН и тот же sid. Зачем: без sid приложение не может ответить на вопрос «сессия AS ещё жива?» (ID-токен живёт до exp, но пользователь мог выйти из AS — exp этого не знает). sid — «ручка», по которой приложение спрашивает AS о состоянии сессии (шаг 2) и по которой AS понимает, ЧТО именно логировать (back-channel, шаг 4). Критично: sid НЕ секрет — он в ID-токене (публичная часть JWT), это идентификатор, не токен доступа.

**Подписи стрелок этого шага**

  • Браузер → Приложение A (РП): login → 302 /callback (sid=S-1 в IDT)
  • **Приложение A (РП)** (собственное действие): сессия: sid=S-1 (httpOnly cookie)

**Что делаете вы (реализация)**

- sid — в ID-токене; одна сессия AS = один sid для всех RP
- sid не секрет (в публичном payload JWT)

**HTTP-трафик / код**

```
ID-токен payload: {
 "sub": "user-123", "sid": "sess-9f2ab7",
 "auth_time": 1762360000, … }
```

#### Шаг 2. Проверка жизни сессии (front-channel, /session endpoint)

**Что происходит**

Одно действие: приложение периодически (или при каждом «важном» переходе) проверяет, жива ли сессия AS: POST на session_check / introspection с sid (+ аутентификация клиента, если endpoint защищённый). AS отвечает: { active: true } — сессия жива; { active: false } — пользователь вышел (или сессия истекла). Механика: приложение НЕ логает пользователя локально — оно спрашивает AS «он ещё там?». Зачем front-channel: back-channel (шаг 4) — push от AS (AS сам сообщает), front-channel — pull от приложения (приложение спрашивает). Оба нужны: push — мгновенно, но требует от AS хранить подписки и шифровать; pull — приложение контролирует частоту, но не мгновенно. Для большинства RP достаточно pull по sid (интроспекция), push — для «мгновенного» logout (банки, админки).

**Подписи стрелок этого шага**

  • Приложение A (РП) → Сервер авторизации (АС): GET /session?sid=S-1 (session-check)
  • **Сервер авторизации (АС)** (собственное действие): sid жива? ✓ (или logout URL в body)

**Что делаете вы (реализация)**

- GET/POST session-check с sid → { active: true|false }
- pull (приложение спрашивает) vs. push (AS сообщает) — разные механизмы

**HTTP-трафик / код**

```
POST /session/check
session_id=sess-9f2ab7&client_id=web-app-01
→ 200 { "active": false }  // пользователь вышел из AS
```

#### Шаг 3. Front-channel logout: пользователь кликнул «Выйти»

**Что происходит**

Два действия (пользователь + браузер): (1) пользователь в приложении нажимает «Выйти»; (2) приложение чистит СВОЮ сессию (cookie, токен в хранилище) и редиректит браузер на end_session_endpoint AS с id_token_hint (ID-токен ТЕКУЩЕЙ сессии — AS по нему находит sid) + post_logout_redirect_uri (предзарегистрированная, куда вернуть). AS: (1) находит сессию по id_token_hint (sid), (2) УНИЧТОЖАЕТ её (все токены сессии мёртвы: AT, RT, и другие ID-токены с тем же sid), (3) 302 на post_logout_redirect_uri. Итог: пользователь вышел из AS — и из приложения. Но: только из ЭТОГО приложения (front-channel = «один браузер, один RP»). Чтобы выйти из ВСЕХ RP — нужен back-channel (шаг 4).

**Подписи стрелок этого шага**

  • Браузер → Приложение A (РП): GET /logout (пользователь кликнул «Выйти»)
  • Приложение A (РП) → Сервер авторизации (АС): end_session_endpoint?id_token_hint&post_logout&state

**Что делаете вы (реализация)**

- Чистим СВОЮ сессию → GET end_session?id_token_hint=…&post_logout_redirect_uri=…
- AS находит сессию по sid (из id_token_hint) и уничтожает её

**HTTP-трафик / код**

```
GET /end-session?id_token_hint=eyJhbG…
  &post_logout_redirect_uri=https://app.example/bye
AS: sid(sess-9f2ab7) → revoke all → 302 app.example/bye
```

#### Шаг 4. Back-channel logout: AS сам сообщает всем RP

**Что происходит**

Одно действие: AS (после уничтожения сессии — front-channel из шага 3, или админ/истечение) шлёт POST logout-notification на registered back_channel_logout_uri каждого RP, которому выдавал токен с этим sid. Тело: logout_token — JWT, подписанный AS, payload: sid, sub, events={oidc:logout}, jti (unique, anti-replay). Аутентификация: подписью logout_token (не client_secret). RP: (1) проверяет подпись (JWKS AS), iss, aud (содержит client_id RP), jti не повторен, (2) находит сессию по sid, (3) уничтожает ЕЁ (локально), (4) 204. Итог: пользователь вышел из AS → все RP, где он был, «узнают» и выгонят его. Критично: RP обязан обработать logout_token как событие безопасности (проверки как на ID-токене), а не «просто POST». Без back-channel — пользователь «выходит» из AS, но в 5 открытых вкладках 5 приложений он «всё ещё вошёл».

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Браузер: 302 post_logout_redirect_uri (чистый браузер)

**Что делаете вы (реализация)**

- AS → POST back_channel_logout_uri (каждый RP): logout_token (JWT: sid, sub, events.oidc:logout, jti)
- RP: подпись + iss + aud + jti → сессию по sid → уничтожить → 204

**HTTP-трафик / код**

```
POST https://app.example/back-logout
Content-Type: application/x-www-form-urlencoded
logout_token=eyJhbG…
  // payload: { "sid": "sess-9f2ab7", "sub": "user-123",
  //   "events": { "oidc:logout": { "at": 1762360300 } },
  //   "jti": "u1x2…" }
→ RP: verify → kill session(sid) → 204
```

#### Шаг 5. Почему нужны ОБА канала

**Что происходит**

Два канала решают разные задачи, и ни один без другого не покрывает сценарий: FRONT-channel (шаг 3) — «я (пользователь в браузере) вышел из ЭТОГО приложения и из AS». Мгновенно, без инфраструктуры, но «одно приложение на один браузер». BACK-channel (шаг 4) — «AS сказал: сессия мёртва, все RP, выгнать». Мгновенно для всех RP, но требует: у AS — хранить подписки (какие RP, какие uri), шифровать/подписывать; у RP — endpoint + проверки logout_token. Матрица: (a) пользователь вышел в приложении → front-channel (AS + это приложение); чтобы выгнать из остальных RP — back-channel; (b) админ отозвал сессию в AS (без браузера) → ТОЛЬКО back-channel (front-channel не работает — нет браузера); (c) сессия истекла по таймауту в AS → back-channel. Итог: front — UX (один клик), back — безопасность (все RP синхронизированы). Production: ОБА.

**Подписи стрелок этого шага**

  • Сервер авторизации (АС) → Приложение B (РП): ⚠ back-channel: POST { sid, sub } на logout_uris
  • **Приложение B (РП)** (собственное действие): сверка sig/sid/sub → уничтожить свою сессию

**Что делаете вы (реализация)**

- Front = «я вышел» (UX, один браузер); Back = «сессия мёртва для всех» (безопасность, все RP)
- Админ-отзыв / таймаут → только back-channel

**HTTP-трафик / код**

```
front: 1 браузер → 1 RP + AS
back:  AS → N RP (все сессии по sid)
production: оба канала активны
```

## 9. Проверка access-токена — локальный JWT и introspection

### Участники диаграммы

| # | Участник |
|---|----------|
| 1 | Сервер авторизации (АС) |
| 2 | Приложение (РП) |
| 3 | JWKS |
| 4 | Злоумышленник |

### Подписи на стрелках переходов

| Шаг | Переход |
|-----|---------|
| 1 | **Сервер авторизации (АС)** (собственное действие): IDT = header.payload.signature (RS256)<br>Сервер авторизации (АС) → Приложение (РП): выдать id_token (подписан прив. ключом kid=k1) |
| 2 | Приложение (РП) → JWKS: GET /.well-known/jwks.json (по kid=k1)<br>JWKS → Приложение (РП): [{ kid:k1, n, e, use:sig }] |
| 3 | **Приложение (РП)** (собственное действие): sig ✓ (RSA) · iss ✓ · aud ✓ · exp ✓ · nonce ✓ |
| 4 | **Сервер авторизации (АС)** (собственное действие): ротация: новый ключ kid=k2, k1 ещё жив (overlap) |
| 5 ⚠ | Приложение (РП) → JWKS: ⚠ unknown kid=k2 → refresh JWKS<br>JWKS → Приложение (РП): [{ kid:k1 }, { kid:k2 }] |
| 6 ⚠ | Злоумышленник → Приложение (РП): ⚠ подделка: JWT без подлинного ключа<br>**Приложение (РП)** (собственное действие): sig ✗ (публичный ключ не подтверждает) → 401 |

### Описание шагов

#### Шаг 1. JWT — три части через точку

**Что происходит**

Одно действие: AS (или приложение-проверяющий) берёт access/id-токен и видит, что это JWT — три base64url-части через «.». Часть 1 — HEADER (JSON): {alg: "RS256", typ: "JWT", kid: "key-2026-11"} — КАК подписан и КАКОЙ ключ. Часть 2 — PAYLOAD (JSON): {iss, sub, aud, exp, iat, jti, scope, …} — ДАННЫЕ. Часть 3 — SIGNATURE: бинарная подпись над «header.payload» (точка в строке сохраняется). Критично: header и payload — НЕ шифрованы, а только base64url-кодированы: любой расшифрует их за секунду. JWT — не «закрытая паковка данных», а «документ с подписью»: содержимое открыто, защищена только ЦЕЛОСТНОСТЬ (подпись). Поэтому в JWT никогда не кладут секреты — «зашифрованный» вид base64 — иллюзия. Три части = «что подписано» (1.2) + «подпись» (3), и проверка = «пересчитать подпись над 1.2 и сравнить с 3».

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): IDT = header.payload.signature (RS256)
  • Сервер авторизации (АС) → Приложение (РП): выдать id_token (подписан прив. ключом kid=k1)

**Что делаете вы (реализация)**

- header+payload — base64url (открыты, не зашифрованы); secrets в JWT не кладут
- JWT = документ с подписью: защищена целостность, не конфиденциальность

**HTTP-трафик / код**

```
eyJhbG…Q2xpbnRfaWQiOiJ3ZWJfYXBwIi0ifQ
 .
eyJpc3MiOiJodHRwczovL2Fz…X0
 .
  (base64url(подпись ECDSA/RSASSA-PSS))
```

#### Шаг 2. Подпись — приватным ключом AS

**Что происходит**

Одно действие: AS строит signing input = BASE64URL(header) + "." + BASE64URL(payload) и подписывает его ПРИВАТНЫМ ключом: для RS256 — RSASSA-PKCS1-v1_5 + SHA-256, для ES256 — ECDSA над SHA-256. Результат — бинарная подпись, base64url → третья часть. Свойство: подпись делает ТОЛЬКО владелец приватного ключа (AS); публичный ключ (у проверяющих) её НЕ сделает — математически невозможно (RSA/EC). Поэтому проверка «это AS подписал» = «подпись сходится с публичным ключом AS». kid в заголовке — «какой именно ключ»: AS может иметь несколько (ротация), и kid выбирает. Без подписи JWT — просто JSON, который кто угодно сошьёт. Подпись — единственное, что делает JWT «токеном», а не «запиской».

**Подписи стрелок этого шага**

  • Приложение (РП) → JWKS: GET /.well-known/jwks.json (по kid=k1)
  • JWKS → Приложение (РП): [{ kid:k1, n, e, use:sig }]

**Что делаете вы (реализация)**

- RS256 = RSASSA-PKCS1-v1_5 + SHA-256; ES256 = ECDSA-SHA256; подписывается "header.payload"
- kid в заголовке — выбор ключа (ротация)

**HTTP-трафик / код**

```
signing_input = b64url(header) + "." + b64url(payload)
sig = ECDSA_P256_SHA256(priv_AS, signing_input)
jwt = signing_input + "." + b64url(sig)
```

#### Шаг 3. JWKS: публичные ключи AS для проверки подписи

**Что происходит**

Одно действие: AS публикует endpoint jwks_uri (из discovery): JSON с массивом ПУБЛИЧНЫХ ключей. Каждый ключ: {kty: "EC", crv: "P-256", x, y, kid: "key-2026-11", use: "sig", alg: "ES256"} — публичная часть (x,y для EC; n,e для RSA). Публичный ключ НЕ секрет: его можно скачать, сохранить, показать. Проверяющий (RP/API) кэширует JWKS и по kid из заголовка JWT находит нужный ключ. Зачем не «один ключ навсегда»: (1) ротация без простоя (шаг 5); (2) компрометация приватного ключа → ротация, старые токены по старому kid — проверяются, новые — по новому; (3) разные use (sig/enc). JWKS — «вывеска»: «вот наши публичные ключи, проверяйте». Кэшировать с TTL + refresh при unknown kid.

**Подписи стрелок этого шага**

  • **Приложение (РП)** (собственное действие): sig ✓ (RSA) · iss ✓ · aud ✓ · exp ✓ · nonce ✓

**Что делаете вы (реализация)**

- GET jwks_uri → {keys:[{kty, crv/x/y|n/e, kid, use:"sig", alg}]}
- Кэш JWKS + refresh при неизвестном kid (ротация в процессе)

**HTTP-трафик / код**

```
GET https://as.example/.well-known/jwks.json
→ { "keys": [
   { "kty":"EC","crv":"P-256","x":"…","y":"…",
     "kid":"key-2026-11","use":"sig","alg":"ES256" },
   { …,"kid":"key-2026-09" } ] }
```

#### Шаг 4. Верификация: подпись + claims

**Что происходит**

Одно действие (атомарно, на RP/API): проверяющий выполняет ПОЛНЫЙ стек: (1) kid → ключ из JWKS; (2) подпись: ECDSA/RSASSA над «header.payload» сходит? нет → reject (подделка или чужой ключ); (3) alg — белый список (RS256/ES256), none → reject; (4) iss == issuer AS (побайтово, из discovery); (5) aud содержит мой client_id/audience; (6) exp > now (skew 30 с); (7) iat <= now+skew; (8) jti — для id_token: nonce. Всё прошло → payload «автентичен от AS, не изменён, в силе». Критично: пропуск ЛЮБОЙ проверки — уязвимость: без exp — вечный токен; без aud — токен для чужого клиента работает; без iss — токен с другого AS. Проверка — ЧЕКЛИСТ, а не «подпись ок → дальше».

**Подписи стрелок этого шага**

  • **Сервер авторизации (АС)** (собственное действие): ротация: новый ключ kid=k2, k1 ещё жив (overlap)

**Что делаете вы (реализация)**

- Стек: kid→ключ, подпись, alg-белый список, iss, aud, exp/iat (skew 30с), nonce (id_token)
- Пропуск любой проверки = уязвимость; alg=none — отклонять всегда

**HTTP-трафик / код**

```
verify(jwt, jwks):
  1) key = jwks[kid]
  2) sig ok?      3) alg ∈ [RS256,ES256]?
  4) iss == "https://as.example"?  5) aud ∋ "web-app-01"?
  6) exp > now-30s?  7) iat <= now+30s?
  → payload (authentic)
```

#### Шаг 5. Ротация ключей без простоя

**Что происходит**

Одно действие: AS публикует НОВЫЙ ключ (kid=key-2026-12) в JWKS, РЯДОМ со старым (kid=key-2026-11). Теперь: новые токены подписываются НОВЫМ (kid=…12); старые токены (kid=…11) продолжают проверяться — ключ ещё в JWKS. Проверяющий при unknown kid (новый kid, кэш старый) → один refresh JWKS → retry. После миграции (все активные токены по новому kid, старые истекли по exp) AS УБИРАЕТ старый kid из JWKS. Итог: ни один момент «простой» — в любой момент работает и старый, и новый. Зачем ротация: (1) периодическая (политика, напр. 90 дней); (2) компрометация приватного (немедленно); (3) смена провайдера/ХСМ. Правило: старый ключ убирать только когда ВСЕ токены по нему истекли (max exp).

**Подписи стрелок этого шага**

  • Приложение (РП) → JWKS: ⚠ unknown kid=k2 → refresh JWKS
  • JWKS → Приложение (РП): [{ kid:k1 }, { kid:k2 }]

**Что делаете вы (реализация)**

- Новый kid РЯДОМ со старым в JWKS; новые токены — новый kid; старый — до истечения его токенов
- Unknown kid → refresh JWKS + один retry; старый убирать только после истечения его токенов

**HTTP-трафик / код**

```
JWKS: [key-2026-11 (старый, active до exp), key-2026-12 (новый, подписывает)]
новый токен: kid=12
старый токен: kid=11 → проверяется
(после exp старых) JWKS: [key-2026-12]
```

#### Шаг 6. Атака: подделка без приватного ключа

**Что происходит**

⚠ Одно событие: атакующий хочет выдать себя за AS: подделывает JWT (свои claims: sub=жертва, aud=приложение, exp=далеко) и шлёт на RP/API. Без приватного ключа AS он НЕ МОЖЕТ подписать: (1) RSA/EC — подпись без приватного математически невозможна (не «сложно», а невозможно); (2) alg=none — проверяющий отклоняет (белый список); (3) «переподписать» чужим ключом — нет доступа к JWKS-ключу (публичный НЕ подписывает); (4) подменить JWKS endpoint (MITM) — TLS + pinning; (5) «забытая» проверка exp/aud — чеклист (шаг 4) ловит. Итог: подделка JWT без приватного ключа AS невозможна при корректной верификации. Все реальные инциденты — НЕ «взлом подписи», а «проверка подписи не делалась / alg=none приняли / iss не сверили». Подпись — крепость; слабое место — ленивая верификация.

**Подписи стрелок этого шага**

  • Злоумышленник → Приложение (РП): ⚠ подделка: JWT без подлинного ключа
  • **Приложение (РП)** (собственное действие): sig ✗ (публичный ключ не подтверждает) → 401

**Что делаете вы (реализация)**

- Подделка без приватного ключа невозможна; реальные инциденты — ленивая верификация (alg=none, нет iss/exp)

**HTTP-трафик / код**

```
⚠ поддельный JWT {sub:жертва, aud:приложение}
→ подпись? (без приватного AS — невозможно)
→ alg=none? reject
→ iss неверный? reject
→ подделка отклонена на любом из уровней
```

## 10. Discovery и регистрация клиента

### Участники диаграммы

| # | Участник |
|---|----------|
| 1 | Приложение (РП) |
| 2 | Сервер авторизации (АС) |
| 3 | JWKS |
| 4 | Регистрация |

### Подписи на стрелках переходов

| Шаг | Переход |
|-----|---------|
| 1 | Приложение (РП) → Сервер авторизации (АС): GET /.well-known/openid-configuration<br>Сервер авторизации (АС) → Приложение (РП): 200 JSON: issuer, endpoints, algorithms, capabilities |
| 2 | Приложение (РП) → JWKS: GET jwks_uri (из metadata)<br>JWKS → Приложение (РП): 200 [{ kty, kid, alg, use, … }] |
| 3 | Приложение (РП) → Регистрация: POST /register (client_id, redirect_uri, …)<br>Регистрация → Приложение (РП): 201 { client_id, client_secret?, jwks_uri } |
| 4 | **Приложение (РП)** (собственное действие): кэш: issuer, token_endpoint, jwks (TTL 1 ч) |
| 5 | Приложение (РП) → Сервер авторизации (АС): GET /token (используем token_endpoint из metadata) |

### Описание шагов

#### Шаг 1. Discovery: один GET — все endpoint URL

**Что происходит**

Одно действие: приложение делает GET на {issuer}/.well-known/openid-configuration (issuer — из discovery-документа AS, формат урн/https) и получает ОДИН JSON со ВСЕМИ endpoint URL: authorization_endpoint, token_endpoint, jwks_uri, end_session_endpoint, revocation_endpoint, userinfo_endpoint, device_authorization_endpoint, backchannel logout, и metadata: issuer, subject_types, id_token_signing_alg_values_supported, code_challenge_methods_supported, grant_types_supported, acr_values_supported. Зачем: НЕ хардкодить URL — AS может иметь dev/stage/prod, и endpoints различаются; приложение берёт ВСЁ из одного GET. Критично: (1) issuer в ответе == запрашиваемый issuer (иначе — чужой документ); (2) TLS обязателен; (3) результат кэшировать (TTL 24ч + ETag), но не «навсегда» (ротация); (4) из discovery — code_challenge_methods_supported: есть S256? нет — PKCE не настроить. Discovery — «меню»: что AS поддерживает.

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): GET /.well-known/openid-configuration
  • Сервер авторизации (АС) → Приложение (РП): 200 JSON: issuer, endpoints, algorithms, capabilities

**Что делаете вы (реализация)**

- GET /.well-known/openid-configuration → все endpoints + metadata
- issuer в ответе == запрошенный; кэш 24ч; S256 в code_challenge_methods?

**HTTP-трафик / код**

```
GET https://as.example/.well-known/openid-configuration
→ {
 "issuer": "https://as.example",
 "authorization_endpoint": "…/authorize",
 "token_endpoint": "…/token",
 "jwks_uri": "…/jwks",
 "end_session_endpoint": "…/end-session",
 "code_challenge_methods_supported": ["S256"],
 "id_token_signing_alg_values_supported": ["ES256","RS256"] }
```

#### Шаг 2. JWKS: публичные ключи AS для верификации подписи

**Что происходит**

Одно действие: приложение берёт jwks_uri из discovery (шаг 1) и делает GET → JSON с массивом публичных ключей AS. Каждый: {kty, crv, x, y, kid, use:"sig", alg}. Это те самые ключи, которыми проверяются подписи JWT (вкладка «Проверка токена», шаг 3): по kid из заголовка JWT выбирается ключ. Критично: (1) JWKS — публичный endpoint (без авторизации): его можно скачать, кэшировать, проверить; (2) в JWKS ТОЛЬКО публичные части (x,y для EC; n,e для RSA) — приватных НЕТ; (3) кэш + TTL + refresh при unknown kid (ротация без простоя); (4) использовать ТОЛЬКО по jwks_uri из discovery (не «поблизости») — защита от MITM-подмены ключей. JWKS и discovery — пара: discovery даёт URL, JWKS даёт ключи.

**Подписи стрелок этого шага**

  • Приложение (РП) → JWKS: GET jwks_uri (из metadata)
  • JWKS → Приложение (РП): 200 [{ kty, kid, alg, use, … }]

**Что делаете вы (реализация)**

- GET jwks_uri → публичные ключи (x,y/n,e) + kid; ТОЛЬКО публичные, приватных нет
- Кэш + TTL + refresh при unknown kid; URL — только из discovery

**HTTP-трафик / код**

```
GET https://as.example/jwks
→ { "keys": [
   { "kty":"EC","crv":"P-256","x":"MFkw…","y":"…",
     "kid":"key-2026-11","use":"sig","alg":"ES256" } ] }
```

#### Шаг 3. Client Registration: динамическая регистрация (RFC 7591)

**Что происходит**

Одно действие: вместо ручной регистрации клиента в AS (заполнить форму, ждать client_id) приложение делает POST на registration_endpoint: JSON с redirect_uris, client_name, grant_types, response_types, application_type, contact, и (для конфиденциальных) token_endpoint_auth_method=private_key_jwt + jwks/jwks_uri. Ответ: 201 с client_id + (опционально) client_secret (для client_secret_basic) + registration_client_uri (для update/delete). Зачем: (1) onboarding самообслуживание — нет «заполнить форму в админке»; (2) интеграция с CI/CD — регистрация клиента как часть деплоя; (3) масштабирование — тысячи клиентов без ручной работы. Критично: (1) registration_endpoint должен быть доступен только доверенным (иначе спам клиентов); (2) response_types/grant_types — валидировать (AS не должен принимать "token" для public client без PKCE); (3) client_secret в ответе — вернуть И УБРАТЬ (не хранить в ответе-логе); (4) RFC 7592 — update/delete по registration_client_uri. Динамическая регистрация — «client как код», не «форма в админке».

**Подписи стрелок этого шага**

  • Приложение (РП) → Регистрация: POST /register (client_id, redirect_uri, …)
  • Регистрация → Приложение (РП): 201 { client_id, client_secret?, jwks_uri }

**Что делаете вы (реализация)**

- POST /register: redirect_uris, grant_types, response_types, token_endpoint_auth_method, jwks
- 201 + client_id; registration_endpoint — только доверенным; secret — вернуть и не логировать

**HTTP-трафик / код**

```
POST /register
{ "redirect_uris": ["https://app.example/callback"],
  "client_name": "Web App",
  "grant_types": ["authorization_code","refresh_token"],
  "response_types": ["code"],
  "token_endpoint_auth_method": "private_key_jwt",
  "jwks_uri": "https://app.example/.well-known/jwks.json" }
→ 201 { "client_id": "web-app-01",
         "registration_client_uri": "…/register/web-app-01" }
```

#### Шаг 4. Кэширование и обновление

**Что происходит**

Одно действие: приложение кэширует discovery-документ + JWKS (TTL 24ч для discovery, 1ч для JWKS — по политике) и обновляет по событиям, а не «каждый запрос»: (1) TTL истёк → refresh; (2) unknown kid в JWKS (JWT с новым kid) → refresh JWKS + retry (ротация); (3) 4xx от endpoint (endpoint переехал) → refresh discovery. Критично: (1) НЕ «каждый запрос — GET discovery»: это 2-3 HTTP на каждый вход, нагрузка; (2) кэш — в памяти + опционально на диске, с ETag/If-Modified-Since (AS может вернуть 304); (3) инвалидация по 4xx (endpoint изменился); (4) negative caching: 5xx от discovery — короткое TTL (5 мин), не «навсегда кэшировать ошибку». Итог: discovery — один раз за 24ч, JWKS — при ротации, а не «на каждый вход».

**Подписи стрелок этого шага**

  • **Приложение (РП)** (собственное действие): кэш: issuer, token_endpoint, jwks (TTL 1 ч)

**Что делаете вы (реализация)**

- Кэш discovery (24ч) + JWKS (1ч); refresh по TTL / unknown kid / 4xx
- Не «на каждый запрос»; negative caching 5xx — короткое TTL

**HTTP-трафик / код**

```
cache.set("discovery", doc, {ttl: 24h, etag})
// refresh triggers:
//  ttl expired | unknown kid | 4xx from endpoint
// negative: 5xx → ttl 5min
```

#### Шаг 5. Использование metadata в запросах

**Что происходит**

Одно действие: приложение ЧИТАЕТ metadata из discovery и ПРИМЕНЯЕТ в запросах: (1) id_token_signing_alg_values_supported → выбрать alg для проверки (RS256/ES256, не «по умолчанию»); (2) code_challenge_methods_supported → S256 есть? → PKCE; (3) grant_types_supported → device_authorization? → device flow доступен; (4) acr_values_supported → какие уровни step-up предложить; (5) require_pushed_authorization_requests → PAR обязателен (вкладка PAR); (6) backchannel_logout_supported → back-channel logout доступен (вкладка Выход). Критично: metadata — не «информация к сведению», а ДАННЫЕ ДЛЯ РЕШЕНИЙ: «S256 в списке? да → настроить PKCE», а не «я надеюсь, что S256 есть». Игнорирование metadata — «работа вслепую»: приложение не знает, что AS поддерживает, и ломается на unsupported_feature. Discovery — «контракт»: что AS обещает, и приложение строит запросы по этому обещанию.

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): GET /token (используем token_endpoint из metadata)

**Что делаете вы (реализация)**

- Metadata → решения: alg, PKCE (S256?), grant_types, acr_values, PAR?, backchannel_logout?
- Не «надеемся, что есть», а «S256 в списке → PKCE»

**HTTP-трафик / код**

```
if (meta.code_challenge_methods_supported ∋ "S256") → PKCE on
if (meta.require_pushed_authorization_requests) → PAR on
if (meta.backchannel_logout_supported) → back-logout on
alg = pick(meta.id_token_signing_alg_values_supported)
```

### Подписи на стрелках переходов

| Шаг | Переход |

| 1 | Приложение (РП) → Сервер авторизации (АС): POST /par (scope, code_challenge, nonce, state, redirect_uri)<br>Сервер авторизации (АС) → Приложение (РП): 201 { "uri":"urn:ietf:params:oauth:request_uri:7f3a…" }  TTL ~60 с · single-use |
| 2 | Приложение (РП) → Браузер: 302 /authorize?client_id&request_uri=urn:… (в URL НЕТ scope/nonce/challenge) |
| 3 | Браузер → Сервер авторизации (АС): GET /authorize?client_id&request_uri — AS достаёт параметры из хранилища<br>**Сервер авторизации (АС)** (собственное действие): validate: client_id ✓ · not used · not expired → extract (TTL ~60 с · single-use) |

### Описание шагов

#### Шаг 1. Запрос авторизации — в POST, не в GET-URL

**Что происходит**

Одно действие: вместо классического GET /authorize?client_id=…&state=…&code_challenge=… (вкладка «Основной вход», шаг 1.3) приложение делает POST на pushed_authorization_request_endpoint: body — ВСЕ параметры авторизации (client_id, redirect_uri, response_type, scope, state, nonce, code_challenge, method). Ответ: 201 с request_uri (краткий идентификатор) + expires_in (обычно 60 с). Зачем: классический GET /authorize?… — ВСЕ параметры в URL: (1) URL в историю браузера, Referer, логи прокси — state/nonce/code_challenge ПУБЛИЧНЫ; (2) очень длинные URL (много параметров) — 2048 limit; (3) атакующий может «засеять» чужим /authorize URL (login CSRF усиление). PAR убирает ВСЁ из URL: в URL остаётся только request_uri (краткий, бессмысленный без access к AS). RFC 9126. Критично: request_uri — ОДНОРАЗОВЫЙ, expires_in 60 с, и AS привязывает его к клиенту (только этот клиент может использовать).

**Подписи стрелок этого шага**

  • Приложение (РП) → Сервер авторизации (АС): POST /par (scope, code_challenge, nonce, state, redirect_uri)
  • Сервер авторизации (АС) → Приложение (РП): 201 { "uri":"urn:ietf:params:oauth:request_uri:7f3a…" }  TTL ~60 с · single-use

**Что делаете вы (реализация)**

- POST /par: ВСЕ параметры в body → 201 {request_uri, expires_in:60}
- URL остаётся чистым: только request_uri (одноразовый, 60с, привязан к клиенту)

**HTTP-трафик / код**

```
POST /par
client_id=web-app-01&redirect_uri=…&response_type=code
&scope=openid profile email&state=…&nonce=…
&code_challenge=…&code_challenge_method=S256
→ 201 { "request_uri": "urn:ietf:params:oauth:request_uri:abc123",
         "expires_in": 60 }
```

#### Шаг 2. 302 на /authorize — только request_uri

**Что происходит**

Одно действие: приложение делает 302 (как в шаге 1.3 Основного входа), НО в URL — только request_uri: /authorize?request_uri=urn:…:abc123. ВСЕ параметры (client_id, state, nonce, code_challenge, scope) — НЕ в URL: они уже в AS (записаны при POST /par). AS по request_uri находит «запасённый» запрос и обрабатывает его. Визуально: URL /authorize?request_uri=urn:… — КРАТКИЙ, не содержит чувствительных параметров. Критично: (1) request_uri — одноразовый (использован → сгорел); (2) expires_in 60 с (не пришёл за минуту → сгорел); (3) только ЭТОТ клиент (client_id, который делал POST /par) может использовать request_uri — чужой клиент с тем же request_uri → 400; (4) PAR обязателен? — из discovery: require_pushed_authorization_requests=true → ВСЕ /authorize только через request_uri (классический GET /authorize?… — 400).

**Подписи стрелок этого шага**

  • Приложение (РП) → Браузер: 302 /authorize?client_id&request_uri=urn:… (в URL НЕТ scope/nonce/challenge)

**Что делаете вы (реализация)**

- 302 /authorize?request_uri=… — ВСЕ параметры НЕ в URL
- request_uri: одноразовый, 60с, только этот клиент; require_pushed…=true → только PAR

**HTTP-трафик / код**

```
302 Found
Location: https://as.example/authorize
  ?request_uri=urn:ietf:params:oauth:request_uri:abc123
// (client_id, state, nonce, code_challenge — НЕ в URL)
```

#### Шаг 3. AS забирает параметры из хранилища

**Что происходит**

Одно действие: AS получает GET /authorize?request_uri=… и: (1) ищет request_uri в хранилище (записан при POST /par); (2) проверяет: жив (expires_in не истёк), одноразовый (не использован), клиент — тот, который делал POST /par (client_id сверить — из аутентификации или из контекста); (3) берёт ВСЕ параметры из записанного запроса (client_id, redirect_uri, state, nonce, code_challenge, scope); (4) АТОМАРНО помечает request_uri использованным (single-use); (5) обрабатывает /authorize как обычно (вход, consent, code). Критично: (1) request_uri — single-use (повторный /authorize?request_uri=… → 400); (2) привязка к client_id (чужой клиент → 400); (3) TTL 60 с (истёк → 400, «запрос просрочен»); (4) параметры из хранилища (НЕ из URL — в URL только request_uri). Итог: «запасённый» запрос извлекается и обрабатывается — пользователь видит обычный /authorize, но параметры пришли «изнутри AS», не из URL.

**Подписи стрелок этого шага**

  • Браузер → Сервер авторизации (АС): GET /authorize?client_id&request_uri — AS достаёт параметры из хранилища
  • **Сервер авторизации (АС)** (собственное действие): validate: client_id ✓ · not used · not expired → extract (TTL ~60 с · single-use)

**Что делаете вы (реализация)**

- AS: request_uri → хранилище → жив? одноразовый? клиент? → параметры → single-use mark → /authorize
- Pовторный/чужой/истёкший request_uri → 400

**HTTP-трафик / код**

```
AS: lookup(request_uri=abc123)
  → {client_id: web-app-01, state, nonce, code_challenge, …}
  → alive(60s)? yes | unused? yes | client matches? yes
  → mark used (atomic)
  → process /authorize (вход → consent → code)
```

#### Шаг 4. Атака: утечка URL

**Что происходит**

⚠ Сценарий, который PAR закрывает: БЕЗ PAR — атакующий «засевает» жертве URL /authorize?client_id=АТАК&state=АТАК&… (через ссылку, email, XSS). Жертва кликает → браузер идёт на /authorize с ПАРАМЕТРАМИ АТАКУЮЩЕГО → если жертва уже вошла в AS → AS выдаёт code (для АТАК) → атакующий обменивает code → привязывает учётку жертвы к СВОЕЙ сессии (login CSRF). С PAR: атакующий НЕ МОЖЕТ «засеять» /authorize?… (все параметры — в POST /par, не в URL). Единственное, что можно засеять — /authorize?request_uri=…, НО: (1) request_uri — одноразовый (атакующий должен сгенерировать СВОЙ через POST /par под СВОИМ client_id); (2) привязан к client_id (жертва, открывшая request_uri атакующего, — client не совпадёт с сессией жертвы); (3) 60 с (засеять и ждать клика за минуту — не успеет). Итог: PAR убирает «URL как вектор атаки» — в URL только краткий одноразовый идентификатор, не параметры.

**Подписи стрелок этого шага**

  • Браузер → Злоумышленник: ⚠ URL с request_uri утекает (Referer, лог прокси, кэш CDN)
  • **Сервер авторизации (АС)** (собственное действие): без client auth не обменять · TTL 60 с · single-use → invalid_request_uri ✗

**Что делаете вы (реализация)**

- БЕЗ PAR: /authorize?… в URL → login CSRF; С PAR: request_uri одноразовый + привязка к client + 60с → засевание бесполезно

**HTTP-трафик / код**

```
⚠ Б ЕЗ PAR: жертва кликает /authorize?client_id=АТАК&…
   → login CSRF (учётка жертвы → сессия атакующего)
С PAR: /authorize?request_uri=… (чужой)
   → client mismatch | expired | used → 400
```
