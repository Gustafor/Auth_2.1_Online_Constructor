# Детальные Use Case — Группа C: валидация/интроспекция/отзыв (RS), device, logout, step-up, keys

Терминология: RP = Релиинг-Партей, AS/OP = Authorization Server / OpenID
Provider, RS = Ресурс-Сервер, End-User = Пользователь.

> UC-15 (Device) и UC-18 (Rotate Keys) — **вне scope Портала** (помечены в AGL):
> UC-15 — устройства без browser, Портал = web app; UC-18 — внутреннее
> управление ключами AS. Детализируются как свойства AS/OP (покрытие scope).

## USE CASE 12 | Introspect Token
| Поле | Содержание |
|------|------------|
| **Описание** | RS проверяет состояние (активен/нет) access token на стороне AS/OP через introspection (для opaque токенов или проверки отзыва). |
| **Используется в** | N/A |
| **Предусловия** | AS/OP поддерживает RFC 7662 (introspection_endpoint в metadata); RS аутентифицирован на introspection (client auth); access token может быть opaque. |
| **Условие успешного завершения** | AS/OP вернул RS JSON-статус токена: `active:true` + claims (scope, sub, aud, iss, exp) или `active:false`; RS принимает решение по доступу. |
| **Условие завершения с ошибкой** | RS не аутентифицирован (401) / token_type не поддерживается (400); статус не получен; (для unknown/отозванного токена ответ `active:false`, НЕ 4xx). |
| **Акторы** | RS (первичный), AS/OP (система). |
| **Стимул** | RS получает запрос с access token (opaque) и проверяет его. |

**ОСНОВНОЙ ПОТОК**
| Шаг | Действие |
|-----|----------|
| 1 | RS формирует POST /introspect: token + (token_type_hint) + client auth. |
| 2 | AS/OP аутентифицирует RS (client auth). |
| 3 | AS/OP находит токен в хранилище. |
| 4 | AS/OP проверяет валидность: существует, не истёк, не отозван, scope. |
| 5 | AS/OP возвращает RS JSON: { active:true, scope, sub, aud, iss, exp, ... } либо { active:false }. |

**РАСШИРЕНИЯ**
| Шаг | Ветвление |
|-----|-----------|
| 2a | RS не аутентифицирован (no/incorrect client auth) → 401, статус не возвращён (Failed End). |
| 3a | Токен неизвестен AS/OP → AS/OP возвращает `active:false` (НЕ 4xx — не раскрывать существование). |
| 4a | Токен истёк → `active:false`. |
| 4b | Токен отозван (UC-14) → `active:false`. |
| 1a | token_type_hint не поддерживается / format кривой → 400. |

**ВАРИАЦИИ**
- К шагу 5: ответ `active:true` + claims или `active:false` — один результат (RS принимает решение).

## USE CASE 13 | Validate Access Token
| Поле | Содержание |
|------|------------|
| **Описание** | RS локально валидирует self-contained access token (JWT, RFC 9068) по JWKS AS/OP — без round-trip к AS/OP. |
| **Используется в** | N/A |
| **Предусловия** | Access token — JWT (typ: at+jwt); JWKS AS/OP опубликован (jwks_uri); RS знает свой aud и ожидаемый issuer. |
| **Условие успешного завершения** | RS проверил подпись (JWKS), iss, aud, exp, nbf, jti и принял access token; доступ к ресурсу разрешён. |
| **Условие завершения с ошибкой** | JWT невалиден (подпись, alg=none, iss/aud, exp/nbf, недоступен ключ); доступ к ресурсу отклонён (401); состояние RS неизменно. |
| **Акторы** | RS (первичный), AS/OP (вторичный — публикует JWKS). |
| **Стимул** | RS получает запрос с JWT access token. |

**ОСНОВНОЙ ПОТОК**
| Шаг | Действие |
|-----|----------|
| 1 | RS извлекает JWT access token из запроса (Authorization: Bearer). |
| 2 | RS декодирует header (alg, kid) и payload. |
| 3 | RS запрещает alg=none; извлекает/каширует JWKS по kid (GET /jwks.json). |
| 4 | RS проверяет подпись JWT ключом из JWKS. |
| 5 | RS проверяет claims: iss (ожидаемый AS/OP), aud (себя), exp (+skew), nbf. |
| 6 | RS проверяет jti (anti-replay, при коротком TTL). |
| 7 | RS разрешает доступ к ресурсу в рамках scope. |

**РАСШИРЕНИЯ**
| Шаг | Ветвление |
|-----|-----------|
| 2a | JWT не распарсился / format кривой → 401 invalid_token (Failed End). |
| 3a | alg=none → 401 (запрещено по RFC 8725). |
| 3b | kid отсутствует в JWKS (новый ключ после ротации) → RS обновляет JWKS; при повторном miss → 401. |
| 4a | Подпись не верна (чужой/отозванный ключ) → 401. |
| 5a | iss != ожидаемый AS/OP → 401. |
| 5b | aud не содержит RS → 401. |
| 5c | exp истёк (с учётом skew) → 401; (nbf в будущем → 401). |
| 6a | jti уже использован (replay) → 401. |

**ВАРИАЦИИ**
- К шагу 4: alg RS256 или ES256 (из JWKS) — один результат (валидный AT).

## USE CASE 14 | Revoke Token
| Поле | Содержание |
|------|------------|
| **Описание** | RP (или RS) отзывает access/refresh token у AS/OP (RFC 7009); отзыванные токены становятся недействительными. |
| **Используется в** | N/A |
| **Предусловия** | AS/OP поддерживает RFC 7009 (revocation_endpoint); requester аутентифицирован (client auth); известен токен для отзыва. |
| **Условие успешного завершения** | AS/OP отозвал токен (и опц. связанные refresh токены); повторное использование токена отклоняется (UC-12/13); ответ 200. |
| **Условие завершения с ошибкой** | Запрос невалиден (нет client auth / кривой format / неподдерживаемый token_type) → 4xx; токен НЕ отозван; (неизвестный/истёкший токен → всё равно 200, не раскрывать). |
| **Акторы** | RP (первичный), AS/OP (система). |
| **Стимул** | RP (или по событию: logout, компрометация) передаёт /revoke. |

**ОСНОВНОЙ ПОТОК**
| Шаг | Действие |
|-----|----------|
| 1 | RP формирует POST /revoke: token + token_type_hint (access_token/refresh_token) + client auth. |
| 2 | AS/OP аутентифицирует запрос (client auth). |
| 3 | AS/OP находит токен. |
| 4 | AS/OP помечает токен отозванным (и опц. связанные refresh токены). |
| 5 | AS/OP возвращает 200 (без body). |

**РАСШИРЕНИЯ**
| Шаг | Ветвление |
|-----|-----------|
| 2a | Нет client auth / неверный → 400/401 invalid_client (Failed End). |
| 3a | Токен неизвестен / уже истёк → AS/OP возвращает 200 (безопасно, не раскрывать существование). |
| 1a | token_type_hint не поддерживается / format кривой → 400 unsupported_token_type. |
| 4a | Отзыв refresh token → AS/OP отзывает ВСЕ связанные токены клиента (каскадный отзыв). |

**ВАРИАЦИИ**
- К шагу 1: отзыв access_token или refresh_token (token_type_hint) — один результат (200, токен недействителен).

|---|---|---|---|---|---|---|

## USE CASE 15 | Complete Device Authorization
| Поле | Содержание |
|------|------------|
| **Описание** | End-User завершает device authorization (RFC 8628) на втором устройстве, устройство поллит /token и получает access token. |
| **Используется в** | N/A |
| **Предусловия** | **ВНЕ SCOPE ПОРТАЛА** (устройства без browser; Портал = web app). AS/OP поддерживает device_authorization_endpoint; устройство (device client) зарегистрировано. |
| **Условие успешного завершения** | AS/OP выдал устройству access token после подтверждения End-User по user_code. |
| **Условие завершения с ошибкой** | End-User отклонил (user_denied) / device_code истёк (expired); токен не выдан; device_code аннулирован. |
| **Акторы** | End-User (первичный), Device/Client (система), AS/OP (система). |
| **Стимул** | Устройство запрашивает /device_authorization. |

**ОСНОВНОЙ ПОТОК**
| Шаг | Действие |
|-----|----------|
| 1 | Устройство передаёт POST /device_authorization (client_id, scope) + client auth. |
| 2 | AS/OP генерирует device_code (одноразовый, TTL) + user_code (короткий) + verification_uri + interval. |
| 3 | AS/OP возвращает устройству response (device_code, user_code, verification_uri, expires_in, interval). |
| 4 | Устройство показывает user_code + verification_uri End-User. |
| 5 | End-User на втором устройстве вводит user_code и логинится (login + consent). |
| 6 | Устройство поллит POST /token (device_code, client_id) по interval. |
| 7 | После подтверждения AS/OP возвращает access token (+ refresh token). |

**РАСШИРЕНИЯ**
| Шаг | Ветвление |
|-----|-----------|
| 2a | Scope / client невалидны → 400, device_code не выдан (Failed End). |
| 5a | End-User отклоняет (не подтверждает) → polling вернёт `error=user_denied` (Failed End). |
| 6a | device_code истёк до подтверждения → polling вернёт `error=expired_token` (Failed End). |
| 6b | Устройство поллит чаще, чем interval → AS/OP возвращает `error=slow_down` (увеличивает interval). |
| 6c | device_code повторно используется → single-use, ошибка. |

**ВАРИАЦИИ**
- К шагу 6: verification_uri (ввести код вручную) или verification_uri_complete (прямая ссылка) — один результат (успех → access token).

|---|---|---|---|---|---|---|
| TC-15-00 | Основной поток: device flow успешен | 1-7 | End-User подтвердил | device_code, user_code, confirmation | access token | UC-15 |
| TC-15-2a | Scope невалиден | 2 | scope="secret" | scope="secret" | 400 | UC-15/2a |

| TC-15-6b | Быстрый polling | 6 | чаще interval | чаще interval | error=slow_down | UC-15/6b |
| TC-15-6c | device_code reused | 6 | повторный code | повторный code | ошибка (single-use) | UC-15/6c |

## USE CASE 16 | Initiate Logout
| Поле | Содержание |
|------|------------|
| **Описание** | Завершение сессии: RP инициирует logout (RP-Initiated) и/или AS/OP уведомляет RP о завершении сессии (Back-Channel Logout); локальные сессии RP завершаются. |
| **Используется в** | N/A |
| **Предусловия** | Сессия End-User активна в AS/OP; RP хранит sid (OIDC Session Mgmt); end_session_endpoint / backchannel_logout_uri зарегистрированы. |
| **Условие успешного завершения** | Сессия End-User в AS/OP завершена; локальная сессия RP завершена (по id_token_hint или logout token); End-User вышел из Portal. |
| **Условие завершения с ошибкой** | Logout не выполнен (id_token_hint невалиден / logout token невалиден); локальная сессия может остаться (недопустимо) → AS/OP/RP гарантирует завершение по минимальной гарантии (сброс локальной сессии). |
| **Акторы** | RP (первичный), End-User (инициатор), AS/OP (система). |
| **Стимул** | End-User запрашивает выход; ИЛИ событие в AS/OP (смена пароля, отзыв, logout, компрометация). |

**ОСНОВНОЙ ПОТОК**
| Шаг | Действие |
|-----|----------|
| 1 | End-User запрашивает выход в RP (Portal). |
| 2 | RP завершает локальную сессию (удаление cookie/storage). |
| 3 | RP формирует редирект на /end-session (id_token_hint + post_logout_redirect_uri + state). |
| 4 | AS/OP валидирует id_token_hint (подпись, aud, iss) и завершает сессию End-User. |
| 5 | AS/OP (Back-Channel) шлёт logout token (JWT: iss, aud, sub, sid, jti, events) на backchannel_logout_uri RP. |
| 6 | RP валидирует logout token (подпись, iss, aud, exp, jti) и завершает локальные сессии по sub+sid. |
| 7 | AS/OP редиректит на post_logout_redirect_uri?state=... ; RP завершает с сообщением «выход выполнен». |

**РАСШИРЕНИЯ**
| Шаг | Ветвление |
|-----|-----------|
| 4a | id_token_hint невалиден (подпись/aud/iss) → AS/OP завершает logout в рамках политики (или отклоняет); мин. гарантия — локальная сессия RP уже сброшена (шаг 2). |
| 6a | Logout token невалиден (подпись/iss/aud/exp) → RP отклоняет; локальная сессия (при смене пароля/отзыве) завершается по событию (Failed End → гарантированный сброс). |
| 6b | jti logout token уже использован (replay) → RP отклоняет повторное завершение. |
| 5a | Back-Channel не поддерживается клиентом (metadata off) → используется только RP-Initiated (валидная вариация). |
| 2a | Локальная сессия уже отсутствует → RP продолжает (идемпотентность). |

**ВАРИАЦИИ**
- К шагу 5: Back-Channel Logout (server-side, рекомендуется) или только RP-Initiated Logout — один результат (сессия завершена).

| Код сценария | Наименование сценария | Номер шага | Описание шага | Входящие данные | Результат шага | Примечание |
|---|---|---|---|---|---|---|
| TC-16-00 | Основной поток: полный logout | 1-7 | End-User выходит | активная сессия, id_token_hint | сессия AS/OP + RP завершены | UC-16 |
| TC-16-4a | id_token_hint невалиден | 4 | поддельный hint | поддельный hint | локальная сессия сброшена (мин. гарантия) | UC-16/4a |
| TC-16-6a | Logout token невалиден | 6 | подпись не верна | подпись не верна | локальная сессия завершена по событию | UC-16/6a |
| TC-16-6b | jti logout replay | 6 | повторный jti | повторный jti | отклонено | UC-16/6b |

## USE CASE 17 | Step-Up Authentication
| Поле | Содержание |
|------|------------|
| **Описание** | AS/OP запрашивает повторную аутентификацию повышенного уровня (MFA) перед выдачей токена на чувствительные операции (RFC 9470). |
| **Используется в** | Authenticate End-User (use case 03) |
| **Предусловия** | AS/OP поддерживает step-up (acr/amr); сессия End-User активна, но уровня недостаточно для операции; RP запрашивает acr=urn:mfa / max_age. |
| **Условие успешного завершения** | End-User прошёл повторную аутентификацию (MFA); AS/OP выдал ID token с acr=urn:mfa, amr=[password,otp], auth_time=now; RP разрешил чувствительную операцию. |
| **Условие завершения с ошибкой** | End-User не прошёл MFA / отклонил; токен повышенного уровня не выдан; чувствительная операция не разрешена; базовая сессия может остаться (не повышена). |
| **Акторы** | End-User (первичный), RP (вторичный — запрашивает), AS/OP (система). |
| **Стимул** | RP вызывает /authorize?step_up_auth=true&acr=urn:mfa&max_age=... для чувствительной операции. |

**ОСНОВНОЙ ПОТОК**
| Шаг | Действие |
|-----|----------|
| 1 | RP формирует /authorize: step_up_auth=true, acr=urn:mfa, max_age, amr, (response_type=code, scope=openid). |
| 2 | AS/OP сравнивает текущий уровень аутентификации End-User (acr) с требуемым (acr=urn:mfa) и возраст сессии (max_age). |
| 3 | AS/OP запрашивает у End-User повторную аутентификацию с MFA (otp/face). |
| 4 | End-User подтверждает MFA. |
| 5 | AS/OP фиксирует новый уровень (acr=urn:mfa, amr=[password,otp], auth_time=now). |
| 6 | AS/OP выдаёт authorization code (с повышенным уровнем). |
| 7 | RP получает ID token с acr=urn:mfa, amr, auth_time; разрешает чувствительную операцию. |

**РАСШИРЕНИЯ**
| Шаг | Ветвление |
|-----|-----------|
| 2a | Текущий уровень уже достаточен (acr ≥ требуемый) и сессия свежая → AS/OP пропускает повторную аутентификацию (валидная вариация, быстрый путь). |
| 3a | End-User не прошёл MFA (неверный otp) → AS/OP возвращает на MFA; при превышении лимита → `error=interaction_required`/отказ (Failed End). |
| 4a | End-User отклоняет повторную аутентификацию → `error=access_denied`, токен повышенного уровня не выдан (Failed End). |
| 5a | MFA-метод недоступен для End-User (не настроен otp) → AS/OP не может выполнить step-up → отказ (Failed End). |
| 7a | RP требует acr выше, чем выдан → RP не разрешает операцию (policy на стороне RP). |

**ВАРИАЦИИ**
- К шагу 3: otp / face / push MFA — один результат (повышенный уровень, acr=urn:mfa).

## USE CASE 18 | Rotate Signing Keys
| Поле | Содержание |
|------|------------|
| **Описание** | AS/OP ротирует ключи подписи JWT (JWKS), публикуя новые ключи и отзывая старые после истечения TTL токенов. |
| **Используется в** | N/A |
| **Предусловия** | **ВНЕ SCOPE ПОРТАЛА** (внутреннее управление ключами AS). AS/OP управляет JWKS; текущие ключи в использовании. |
| **Условие успешного завершения** | AS/OP опубликовал новые ключи (kid) в JWKS; новые токены подписываются новым ключом; старые ключи остаются в JWKS до истечения TTL токенов, затем удаляются. |
| **Условие завершения с ошибкой** | Ротация не выполнена (сбой публикации JWKS); AS/OP продолжает использовать прежний ключ; валидация токенов (UC-04/13) не прерывается (мин. гарантия — старые ключи доступны). |
| **Акторы** | AS/OP (система, внутренний процесс). |
| **Стимул** | Наступление срока ротации ключей (политика AS/OP) или отзыв компрометированного ключа. |

**ОСНОВНОЙ ПОТОК**
| Шаг | Действие |
|-----|----------|
| 1 | AS/OP генерирует новую пару ключей подписи (kid, alg). |
| 2 | AS/OP публикует новые ключи в JWKS (GET /jwks.json) — наряду со старыми. |
| 3 | AS/OP переключает подпись новых токенов на новый kid. |
| 4 | AS/OP продолжает выдавать старые ключи в JWKS для валидации ранее выпущенных токенов. |
| 5 | После истечения максимального TTL токенов (signing) AS/OP удаляет старые ключи из JWKS. |

**РАСШИРЕНИЯ**
| Шаг | Ветвление |
|-----|-----------|
| 2a | Публикация JWKS не удалась (ошибка storage) → AS/OP откатывает ротацию, продолжает со старым ключом (Failed End для ротации; валидация не прерывается). |
| 4a | Запрошен валидацией токен со старым kid, который ещё в JWKS → валидация успешна (валидная вариация, overlap). |
| 5a | Удаление старых ключей произошло раньше, чем истёк TTL токенов → валидация старых токенов временно падает (дефект; AS/OP должен задерживать удаление). |

**ВАРИАЦИИ**
- К шагу 1: алг RS256 или ES256 (из политики AS/OP) — один результат (ротированный ключ в JWKS).
